## Store choices (by access pattern)

| Data | Store | Why |
|---|---|---|
| User / profile | SQL | Relational, strong authz |
| Groups / members | SQL | Transactions on membership |
| Conversations | SQL | Small metadata |
| Messages | Wide-column / distributed doc store | Huge write+time range reads |
| Presence / session | Redis | Ephemeral |
| Media | Object storage | Blobs |
| Search | Search index | Inverted index |
| Events | Kafka | Stream |
| Analytics | Warehouse | OLAP |

## Message sharding

<Mermaid chart={`flowchart TB
  MDB[Message DB]

  S1 --> C1[conv hash range]

| Topic | Recommendation |
|---|---|
| Shard key | `conversationId` (keeps a chat together) |
| Avoid userId-only | Splits a conversation across shards |
| Hot partition | Mega-groups → dedicated cluster / fan-out service |
| Rebalance | Consistent hashing; dual-write migration |
| Replicas | Quorum writes; read replicas for history |
| Consistency | Read-your-writes via primary for sender |

### Unread counts

Redis counter per user+conversation (approx)

## Interview explanation

> Metadata in SQL, messages in a sharded append-friendly store keyed by conversationId, media in object storage, presence in Redis. Shard to keep ordering and range queries local.

## Corner case

Shard outage → fail only conversations on that shard; multi-shard clients show partial degradation.
