## The problem

An API serves many customers. One tenant suddenly sends a huge burst and consumes shared capacity. We need to enforce limits fairly without adding significant latency to every request.

## Requirements

Examples: 100 requests/second per user, burst capacity of 200, separate limits for expensive endpoints, and predictable behavior during limiter failure.

## Token bucket

A token bucket stores a token count and refill rate. Each request consumes a token. Bursts are allowed up to the bucket capacity, while the refill rate controls sustained traffic.

```text
Request → Rate Limiter → API
              |
             Redis
```

## Distributed implementation

All application instances need a shared decision. Redis is useful because a small state update can be made atomically. A Lua script can calculate elapsed time, refill tokens and consume one token as a single operation.

## Key design

A key might be `rate:{tenant}:{route}`. The key must match the business isolation boundary. If the requirement is per-user, using an IP-only key is the wrong abstraction.

## Failure handling

The critical question is whether a limiter outage should be fail-open or fail-closed. For a public read API, fail-open for a short window may protect availability. For a security-sensitive operation, fail-closed may be safer. The choice belongs to the business risk model.

## Scaling

A single Redis shard can become hot for a globally popular tenant. Mitigations include local pre-limiting, hierarchical limits, sharded keys or regional limiters.

## Trade-offs

| Strategy | Benefit | Cost |
|---|---|---|
| Token bucket | Burst + sustained control | State management |
| Fixed window | Simple | Boundary bursts |
| Sliding window | More accurate | More state |
| Local limiter | Very low latency | Cross-instance inconsistency |
| Redis limiter | Shared decision | Redis dependency |

## Staff-level discussion

A mature design distinguishes enforcement from observability, defines fail-open/closed behavior per endpoint, and treats quotas as a product contract rather than only an infrastructure setting.
