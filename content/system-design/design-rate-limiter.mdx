## 30-second answer

Shared Redis **token bucket** with **Lua** so refill+consume is atomic across pods; gateway/WAF for floods; app library for JWT identity; hierarchical AND limits; **429 + Retry-After**; fail-closed on payments, fail-open on public reads; watch hot keys and Redis p99.

## The problem

`POST /payments` jumps from 1K to 50K RPS (bug, bot, retry storm). Without admission control you burn thread pools, DB pools, Kafka buffers, and downstream providers — then retries amplify the outage.

## Requirements

Per user / tenant / API / IP / global limits (AND). Burst + sustained. p99 check &lt; 5–10 ms. Explicit fail-open / fail-closed / local-fallback. Dynamic config. Observability.

## Algorithm choice

| Algorithm | Burst | Memory | Typical use |
| --- | --- | --- | --- |
| Fixed window | Boundary 2× | O(1) | Coarse gateway |
| Sliding log | Strict | High | Billing-grade |
| Sliding counter | Medium | O(1) | Cheap approx |
| **Token bucket** | Controlled | O(1) | **APIs (default)** |
| Leaky bucket | Low | O(1) | Traffic shaping |

## Distributed implementation

All pods share Redis. **Never GET then SET** — race admits twice. One Lua `EVAL` on a single key: refill, consume, `PEXPIRE`.

## Failure & scale

Payments fail-closed; public GET may fail-open. Hot keys need local pre-limit / sharding. Multi-region exact globals are usually approximate — say that out loud.
