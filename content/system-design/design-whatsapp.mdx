## How to use this page (5/15/30 min)

This is a **WhatsApp-like industry design**, not a claim about private WhatsApp internals. In an interview, say that clearly, then design a messaging platform with similar product behavior: low-latency chat, offline delivery, groups, media, calls, linked devices, privacy, and large-scale reliability.

### Pick your mode

| If you have | Read these sections | Goal |
|---|---|---|
| 5 minutes | Memory sheet + story + spoken answer | Deliver a crisp Staff-level answer. |
| 15 minutes | Add protocols, one-to-one, groups, offline, Kafka, Redis | Handle the first wave of follow-ups. |
| 30 minutes | Add sharding, multi-region, media, calls, failures, Q&A | Drive the interview instead of reacting. |

### Mental model

```text
User action -> durable fact -> ordered stream -> delivery decision -> client ACK -> derived state
```

WHAT: a chat system is a **durable event system with realtime edges**.  
HOW: clients talk to gateways; services persist source-of-truth rows; Kafka fans internal work; Redis holds ephemeral presence; object storage holds media; WebRTC carries call media.  
WHY: the system must survive disconnects, retries, duplicate sends, hot groups, region issues, and app restarts without losing messages.

### Interview promise

By the end you should be able to say:

```text
Phone does not send a WhatsApp message directly to another phone.
Phone -> WhatsApp-like edge -> backend -> durable storage -> delivery pipeline -> recipient edge.
Kafka is internal service-to-service infrastructure, not phone-to-phone transport.
```

Keep repeating the Staff-level invariant:

| Invariant | Why it matters |
|---|---|
| Persist before delivery | A delivered message cannot disappear after a crash. |
| Idempotency by client message id | Mobile retries are normal, not exceptional. |
| Ordering per conversation | Global ordering is unnecessary and expensive. |
| Presence is ephemeral | Redis can be rebuilt; the message log cannot. |
| Kafka is internal only | Clients use HTTPS/WebSocket/WebRTC, not Kafka. |

## The interview story (Alice → Bob)

Start with a story. Interviewers remember stories better than component lists.

Alice opens her phone on a train. Her app already has a WebSocket connection to a nearby edge gateway. She types "on my way" to Bob and presses send.

The client creates a `clientMsgId`, encrypts the payload for Bob's devices, and sends a small envelope to the backend. The Message Service authenticates Alice, checks that Alice can send to the conversation, assigns a server id and a monotonically increasing sequence number for that conversation, stores the message, then publishes an internal event.

A Delivery Worker consumes the event. It checks Redis to see whether Bob's devices are online. Bob's laptop is connected; his phone is offline. The worker pushes the message to the laptop's WebSocket node and stores pending delivery state for the phone. Bob's laptop sends a delivery ACK. Later Bob opens the phone, syncs missed messages, and sends read receipts from both devices.

### Story-first answer outline

| Beat | Say this |
|---|---|
| Client edge | Alice uses WebSocket for realtime send and receive. |
| Durable core | The backend stores message metadata and encrypted payload before fan-out. |
| Internal async | Kafka decouples commit path from delivery, notifications, indexing, analytics, and retries. |
| Recipient edge | Delivery workers route to Bob's current WebSocket node using Redis presence. |
| Offline | If Bob is offline, store pending state and send mobile push as a wake-up, not as the source of truth. |
| ACKs | Sent, delivered, and read are separate state transitions. |
| Scale | Partition by conversation id for ordering; shard users and conversations independently. |

### What makes it Staff-level

A junior answer says "use WebSockets and Kafka". A Staff answer explains:

- exactly what is durable and what is ephemeral;
- why Kafka does not give client delivery by itself;
- where ordering is enforced;
- how duplicates are prevented;
- what happens when Redis, Kafka, a gateway, or a region fails;
- why groups and linked devices change write amplification;
- what is different for text, media, calls, status, search, payments, and live location.

## Requirements & estimation

### Functional requirements

| Area | Requirement | Notes |
|---|---|---|
| Identity | Register users by phone number or account id | Actual product policy can vary. |
| Contacts | Discover contacts who are users | Privacy-aware hash upload or permissioned sync. |
| One-to-one | Send text, emoji, reactions, edits, deletes | Conversation-scoped ordering. |
| Groups | Create groups, membership, roles, send to many users | Needs fan-out strategy. |
| Offline | Deliver after reconnect | Durable unread and pending state. |
| Receipts | Sent, delivered, read | Per recipient and per device details may be compacted. |
| Presence | Online, last seen, typing | Ephemeral with privacy controls. |
| Media | Upload/download images, files, voice notes | Object storage plus CDN. |
| Calls | Audio/video/group calls | WebRTC media, signaling through backend. |
| Linked devices | Multiple devices per account | Recipient is user-device, not just user. |
| Status | Temporary broadcast stories | Expiring media and viewer state. |
| Search | Search local or server-indexed messages | Usually privacy-constrained. |
| Payments | Optional money transfer flow | Strong consistency and audit. |

### Non-functional requirements

| Requirement | Target talking point |
|---|---|
| Latency | p99 &lt; 200ms for send ACK in-region; delivery best effort near realtime. |
| Availability | Messaging path should degrade, not go fully dark on cache or Kafka incidents. |
| Durability | Once accepted, a message survives process, node, and zone failures. |
| Ordering | Per conversation ordering, not global ordering. |
| Privacy | End-to-end encrypted payload design; backend routes opaque envelopes. |
| Scale | Hundreds of millions of daily active users; millions of concurrent sockets. |
| Cost | Media and fan-out dominate; use object storage, CDN, batching, compaction. |
| Abuse | Rate limits, device trust, spam controls, group invite controls. |

Use simple round numbers. The exact numbers matter less than showing how they shape design.

| Input | Example |
|---|---:|
| Daily active users | 500M |
| Concurrent connections | 50M |

| Text messages per day | 50B |

| Text write volume | 50 TB/day before replication/indexes |

| Observation | Design implication |
|---|---|
| Connections are long-lived | Use a stateless WebSocket fleet plus external session registry. |

### Request path vs async path

```text
Synchronous send path:
Client -> WS Gateway -> Message Service -> Message DB -> ACK to sender

Asynchronous side effects:
MessageCreated -> Kafka -> delivery, push, group fan-out, index, metrics, abuse checks
```

### What is not in this diagram

| Not shown | Reason |
|---|---|
| Exact encryption protocol | Mention end-to-end encryption at HLD, do not pretend to know private internals. |
| ML moderation details | For encrypted messages, moderation moves to metadata, reports, or client-side signals. |
| Vendor-specific databases | Choose generic stores first, then map to Cassandra/DynamoDB/MySQL/Postgres as follow-up. |
| Phone-to-phone Kafka | There is none. Kafka is internal. |

### Boundary summary

| Component | Stores durable state? | Scales by |
|---|---|---|
| WebSocket Gateway | No | connection count, region, user affinity |
| Message Service | Writes durable state | conversation shard |
| Delivery Service | Mostly no | event partitions and session fan-out |
| Redis Presence | No | user id hash and region |
| Kafka | Durable internal log | topic partitions |
| Message DB | Yes | conversation id or bucketed conversation id |
| Object Storage | Yes | object key prefix and region |

## Communication protocols (table + Mermaid)

A WhatsApp-like system is not one protocol. It uses the right protocol for each job.

| Flow | Client protocol | Backend protocol | Why |
|---|---|---|---|
| Login, profile, contacts | HTTPS/JSON or HTTPS/gRPC | gRPC/HTTP | Request-response, cacheable, easy auth. |
| Send/receive text | WebSocket | gRPC plus Kafka events | Low-latency bidirectional edge, durable backend. |
| Message sync after offline | HTTPS page fetch or WebSocket request | DB query | Efficient backfill and pagination. |
| Media upload | HTTPS multipart or resumable upload | Object storage API | Large bytes bypass message DB. |
| Media download | HTTPS CDN | Object storage/CDN | Cheap global reads. |
| Typing and presence | WebSocket | Redis pub/sub or streams | Ephemeral and fast. |
| Call setup | WebSocket signaling | Call service and Redis | Exchange offers, answers, ICE candidates. |
| Call media | WebRTC SRTP | TURN/SFU if needed | Realtime media path. |
| Push notification | APNS/FCM | Push provider API | Wake offline mobile device. |
| Internal workflows | None on phone | Kafka | Decouple backend services. |

### Send protocol decision

| Option | Good | Bad | Use? |
|---|---|---|---|
| HTTPS polling | Simple | High latency, wasteful | Backup and sync, not primary realtime. |
| Server-Sent Events | Simple server push | Client-to-server still needs separate channel | Rare for chat app primary flow. |
| WebSocket | Bidirectional, mobile friendly enough | Requires connection fleet and heartbeats | Primary realtime channel. |
| MQTT-like protocol | Efficient pub/sub semantics | More custom infra and client complexity | Possible, but explain similarly to WebSocket. |
| Kafka to phone | None for mobile clients | Not suitable, exposes infra, heavy clients | No. Kafka is not phone-to-phone. |

### Staff sound bite

```text
WebSocket gives the realtime pipe, but not durability, ordering, replay, or cross-service fan-out.
Those come from Message DB, conversation sequencing, sync APIs, Kafka, and ACK processing.
```

| Question | Staff answer |
|---|---|

## One-to-one messaging (sequence Mermaid + ticks state machine)

### The send path

WHAT: Alice sends an encrypted envelope to Bob.  
HOW: backend validates, sequences, persists, emits event, delivers to Bob's online devices, and records ACKs.  
WHY: the phone can retry safely, gateways can crash, and Bob can sync later.

### Tick semantics

| UI state | Backend meaning | Caveat |
|---|---|---|
| Clock | Client has local pending message | May not have reached server. |
| Single tick | Server persisted message | Not proof Bob has received it. |
| Double tick | At least one recipient device delivered | For groups, can be partial. |
| Blue/read | Recipient read progress crossed message seq | Privacy settings may suppress. |

### Persist plus Kafka sketch

This is conceptual Java, not production-ready code.

```java
public final class MessageCommandHandler {
  private final MessageRepository messages;
  private final IdempotencyRepository idempotency;
  private final ConversationSequencer sequencer;
  private final TransactionRunner tx;
  private final KafkaTemplate<String, MessageCreatedEvent> kafka;

  public SendResult send(SendMessageCommand cmd) {
    return tx.required(() -> {
      Optional<SendResult> previous = idempotency.find(cmd.senderId(), cmd.clientMsgId());
      if (previous.isPresent()) {
        return previous.get();
      }

      long seq = sequencer.nextSeq(cmd.conversationId());
      MessageRow row = MessageRow.accepted(
          cmd.conversationId(),
          seq,
          cmd.senderId(),
          cmd.clientMsgId(),
          cmd.encryptedPayloadRef(),
          Instant.now());

      messages.insert(row);
      SendResult result = new SendResult(row.serverMsgId(), row.conversationId(), seq);
      idempotency.record(cmd.senderId(), cmd.clientMsgId(), result);

      kafka.send(
          "message-created",
          cmd.conversationId().toString(),
          MessageCreatedEvent.from(row));

      return result;
    });
  }
}
```

In a real system, consider the **transactional outbox** pattern so DB commit and event publication do not split-brain.

  TX --> I[Insert idempotency key]
  TX --> O[Insert outbox event]
  O --> P[Outbox publisher]
  P --> K[Kafka]
  K --> D[Delivery workers]
`} />

## Group messaging (fan-out write vs read)

Groups are the first major scaling fork.

### Fan-out options

| Strategy | What | Good | Bad | Use for |
|---|---|---|---|---|
| Fan-out on write | Create per-recipient inbox entries when sender sends | Fast reads and push | Expensive writes for large groups | Small and medium groups |
| Fan-out on read | Store once; readers query group stream | Cheap writes | Read path must merge and track progress | Very large groups |
| Hybrid | Write fan-out for active or small groups, pull for huge groups | Balanced | More complexity | Staff answer |

### Membership versioning

A group message must be evaluated against a membership view.

| Problem | Solution |
|---|---|
| Bob leaves while Alice sends | Use membership version or joinedSeq/leftSeq. |
| Admin removes member | New membership event takes effect at a sequence boundary. |
| New member joins | New member receives messages with seq greater than joinSeq unless history sharing is enabled. |
| Group settings change | Settings are conversation events with sequence numbers. |

### Group receipt compaction

For small groups, exact per-user read receipt is fine. For huge groups, store aggregate counters and only fetch details on demand.

| Receipt type | Small group | Large group |
|---|---|---|
| Delivered | Per user | Count plus sampled/details page |
| Read | Per user | Count plus top recent readers |
| Sender UI | Full list | Partial list and count |
| Storage | `message_recipient_state` rows | `group_message_stats` plus sparse details |

### Hot group protection

```text
If one celebrity-scale group creates too many delivery tasks:
- batch fan-out by member shard;
- prioritize online active members;
- let inactive members pull on reconnect;
- cap receipt detail work;
- isolate hot group partitions.
```

## Ordering & idempotency

Ordering and duplicate handling are where many interviews turn.

### Ordering goals

| Scope | Need total order? | Reason |
|---|---|---|
| Entire platform | No | Impossible and unnecessary. |
| Per user inbox | Partial | Multiple conversations can interleave. |
| Per conversation | Yes | Chat history must be coherent. |
| Per sender device before server ACK | Local only | Client can show pending order. |
| Across linked devices | Eventually consistent | Device clocks differ; server sequence wins. |

### Conversation sequencing

<Mermaid chart={`flowchart LR
  A[Send request] --> H[Hash conversationId]
  H --> P[Owner partition]
  P --> L[Conversation sequence allocator]
  L --> DB[Insert seq N]
  DB --> K[Kafka key conversationId]
  K --> C[Consumers process in partition order]
`} />

### Idempotency key

Use a stable client-generated id. The same send retry must map to the same accepted message.

| Field | Purpose |
|---|---|
| `senderId` | Prevent different users colliding. |
| `clientMsgId` | Stable UUID generated once per local message. |
| `conversationId` | Validates duplicate is for same conversation. |
| `payloadHash` | Optional safety check for inconsistent retry. |
| `serverMsgId` | Returned answer for duplicates. |

### Idempotency sketch

```java
public final class IdempotentSendService {
  private final IdempotencyRepository keys;
  private final MessageRepository messages;

  public SendResult sendOnce(SendMessageCommand cmd) {
    IdempotencyKey key = new IdempotencyKey(cmd.senderId(), cmd.clientMsgId());

    try {
      keys.insertPending(key, cmd.conversationId(), cmd.payloadHash());
    } catch (DuplicateKeyException duplicate) {
      return keys.awaitFinalResult(key)
          .orElseThrow(() -> new RetryableConflictException("send still committing"));
    }

    try {
      MessageRow row = messages.createWithNextSequence(cmd);
      keys.markSucceeded(key, row.serverMsgId(), row.serverSeq());
      return new SendResult(row.serverMsgId(), row.conversationId(), row.serverSeq());
    } catch (RuntimeException failure) {
      keys.markFailedIfRetryable(key, failure.getClass().getSimpleName());
      throw failure;
    }
  }
}
```

### Ordering state diagram

<Mermaid chart={`stateDiagram-v2
  [*] --> ClientPending
  ClientPending --> ServerSequenced: seq assigned
  ServerSequenced --> VisibleInHistory: persisted
  VisibleInHistory --> DeliveredOutOfOrder: later seq arrived first on client
  DeliveredOutOfOrder --> ReorderedBySeq: missing seq fetched
  VisibleInHistory --> Stable: contiguous seq available
  Stable --> [*]
`} />

### Common pitfalls

| Pitfall | Better answer |
|---|---|
| Order by client timestamp | Client clocks lie; use server sequence. |
| One Kafka partition for all messages | Bottleneck and global blast radius. |
| Random Kafka key | Breaks conversation ordering. |
| Assume exactly-once delivery to phone | Use at-least-once plus idempotent client handling. |
| Deduplicate by message text | Same text can be sent twice intentionally. |

### Out-of-order client handling

```text
Client receives seq 100, then seq 102.
Client renders 100 and marks 102 as buffered.
Client asks sync API for seq 101 or waits briefly.
When 101 arrives, client renders 101 then 102.
```

### Presence Java sketch

```java
public final class PresenceHeartbeatHandler {
  private final RedisClient redis;
  private final Clock clock;

  public void heartbeat(UserId userId, DeviceId deviceId, ConnectionId connectionId, NodeId nodeId) {
    Instant now = clock.instant();
    SessionRecord session = new SessionRecord(userId, deviceId, connectionId, nodeId, now);

    redis.setex("session:" + connectionId.value(), 45, Json.write(session));
    redis.sadd("node:" + nodeId.value() + ":sessions", connectionId.value());
    redis.setex("presence:user:" + userId.value(), 45, "online");
  }

  public PresenceView lookup(UserId userId) {
    String value = redis.get("presence:user:" + userId.value());
    return value == null ? PresenceView.offlineOrUnknown() : PresenceView.online();
  }
}
```

## Redis & distributed lock

Redis is a **speed layer**, not the source of truth for messages.

### Redis use cases

| Use case | Why Redis fits | Source of truth |
|---|---|---|
| Presence | Low-latency TTL keys | None; ephemeral truth. |
| Session routing | Fast lookup user -> node | Rebuilt from active sockets. |
| Rate limiting | Atomic counters with TTL | Policy config. |
| Idempotency cache | Fast duplicate check | Durable idempotency table if needed. |
| Group metadata cache | Reduce DB reads | Group DB. |
| Distributed locks | Short critical sections | DB constraints or fencing tokens. |

<Mermaid chart={`flowchart TD
  WS[WebSocket Node] -->|heartbeat setex| R[(Redis)]
  D[Delivery Worker] -->|lookup sessions| R
  API[API Gateway] -->|rate counters| R
  G[Group Service] -->|metadata cache| R
  R -->|miss| DB[(Durable DB)]
  L[Lock Client] -->|set nx px| R
  L -->|fencing token| DB
`} />

### Distributed lock pattern

Use locks sparingly. Prefer database uniqueness, compare-and-swap, or partition ownership. If you need a Redis lock, use a lease plus fencing token.

<Mermaid chart={`sequenceDiagram
  participant W1 as Worker 1
  participant R as Redis
  participant DB as DB with fencing
  participant W2 as Worker 2
  W1->>R: SET lock key token1 NX PX 5000
  R-->>W1: ok
  W1->>DB: write with fencing token 101
  W2->>R: SET lock key token2 NX PX 5000
  R-->>W2: ok after lease expiry
  W2->>DB: write with fencing token 102
  W1->>DB: late write token 101
  DB-->>W1: reject stale token
`} />

### Lock decision table

| Problem | Use lock? | Better primitive |
|---|---|---|
| Assign conversation sequence | Usually no | Single partition owner or DB atomic counter. |
| Create direct conversation once | No | Unique index on normalized participants. |
| Process media job once | Maybe | Idempotent job row and retry state. |
| Group admin mutation | Maybe | Versioned compare-and-swap. |
| Prevent two WebSocket owners for same device | Maybe | Lease with fencing token. |

### Redis failure behavior

| Redis issue | Impact | Degradation |
|---|---|---|
| Presence cache down | Online lookup fails | Treat as unknown, rely on push and sync. |
| Rate limit cache down | Abuse risk | Local limits plus stricter edge defaults. |
| Group cache stale | Wrong metadata risk | Version check with DB. |
| Lock unavailable | Mutations slow or fail closed | Use DB constraints for critical writes. |

### Why Kafka is useful

| Need | Kafka helps by |
|---|---|
| Decoupling | Message send does not wait for every side effect. |
| Replay | Rebuild derived indexes or retry delivery tasks. |
| Ordering | Key by conversation id to keep per-conversation order in a partition. |
| Backpressure | Consumers lag without taking down writers immediately. |

### Failure matrix

| Failure | What users see | System response |
|---|---|---|
| Kafka producer fails before DB commit | Send fails | Client retries same clientMsgId. |

| Consumer crashes after delivery before offset commit | Duplicate delivery possible | Client and receipt update are idempotent. |
| Consumer commits before delivery | Dangerous if no durable delivery task | Use transactional task table or commit after durable handoff. |
| Kafka lag grows | Delayed delivery and side effects | Autoscale consumers, shed low-priority work. |
| Poison event | Partition blocked | Dead-letter with alert after bounded retries. |

## Corner cases & what-if Q&A (table of 25)

| # | What if interviewer asks... | Staff answer |
|---:|---|---|
| 1 | Alice taps send twice because the network is slow. | Use `clientMsgId` idempotency; duplicate retries return the same `serverMsgId`. |
| 2 | Message DB commits but Kafka publish fails. | Use transactional outbox; sender ACK can succeed, publisher retries event until Kafka receives it. |
| 3 | Kafka delivers the same event twice. | Consumers are idempotent by conversationId, seq, recipient/device. |
| 4 | Bob receives seq 12 before seq 11. | Client buffers or fetches the gap; server sequence is source of display order. |
| 5 | Redis says Bob is offline but he is online. | Push may be sent unnecessarily; Bob also syncs via WebSocket, no message loss. |
| 6 | Redis says Bob is online but socket is dead. | Delivery attempt fails; worker retries and client sync repairs. |
| 7 | A WebSocket node dies with 1M connections. | Clients reconnect with jitter; session registry TTL expires; load balancer spreads reconnects. |
| 8 | A group has 100K members. | Use hybrid fan-out: active members get write fan-out, inactive members pull from group stream. |
| 9 | Bob leaves a group while Alice sends. | Membership version or join/left sequence defines who receives the message. |
| 10 | Sender edits a message. | Store edit event/version with policy checks; deliver as ordered conversation event. |
| 11 | Sender deletes for everyone. | Store tombstone event; clients render deletion if policy window allows. |
| 12 | Bob blocks Alice. | Send authorization checks block list before accepting new direct messages. |
| 13 | Alice sends media and app closes mid-upload. | Resumable upload; message is not finalized until media is uploaded or marked pending. |
| 14 | CDN is down in one region. | Fallback to origin or alternate CDN, with degraded media download but chat text continues. |
| 15 | Push provider is down. | Offline users may not wake immediately; durable sync delivers when they open app. |
| 16 | Kafka lag is high. | Send ACK can still work if DB is healthy; delivery side effects lag; autoscale and shed low priority consumers. |
| 17 | DB shard is hot. | Split hot conversation buckets, isolate large groups, move partitions, cache metadata, throttle abusive senders. |
| 18 | Need exactly-once message delivery. | Phones get at-least-once delivery with idempotency; exactly-once end-to-end is not realistic. |
| 19 | Need global ordering. | Reject requirement; per-conversation ordering is the product invariant. |
| 20 | Bob has four linked devices. | Encrypt or wrap payload per device, track delivery per device, roll up user-level read state. |
| 21 | Device keys change. | Fetch latest key bundle, mark safety change, reject stale envelopes if policy requires. |
| 22 | Search message text under E2E encryption. | Prefer local device index; server plaintext index conflicts with privacy. |
| 23 | Group call has 30 people. | Use SFU, simulcast/adaptive bitrate, regional routing, participant limits. |
| 24 | Payment notification is lost. | Ledger remains source of truth; chat message can be retried or reconstructed. |
| 25 | Region A fails during send. | If commit did not happen, retry to failover region; if committed, replicate/outbox drives recovery depending on RPO. |

## 5 / 15 / 30 minute spoken answers

### 5-minute answer

"I’ll design a WhatsApp-like system, not private WhatsApp internals. The main path is: mobile client connects to an edge gateway over WebSocket for realtime messaging and HTTPS for normal APIs and media upload. When Alice sends Bob a message, the Message Service validates auth and membership, deduplicates using Alice’s `clientMsgId`, assigns a server sequence number for that conversation, persists the encrypted message envelope, and returns a sent ACK. After persistence, an outbox publishes a `MessageCreated` event to Kafka. Kafka is internal only; phones do not talk to Kafka.

Delivery workers consume the event, look up Bob’s online devices in Redis presence, and push over the owning WebSocket nodes. If Bob is offline, the message remains durable and the Push Service sends APNS/FCM as a wake-up. Bob’s client syncs missed messages after reconnect. Delivered and read receipts are separate idempotent updates, usually high-water marks per conversation. For groups, I use fan-out on write for small groups and hybrid/pull for huge groups. Media goes to object storage and CDN, with the message row storing a media reference. Calls use WebSocket signaling and WebRTC media through direct, TURN, or SFU paths."

### 15-minute answer

"I would split the design into edge, core services, data, and workers. Edge has API Gateway, WebSocket Gateway, Upload Gateway, and Call Signaling. Core services include User, Contact, Conversation, Group, Message, Delivery, Media, Status, Search, and Payment if required. Data includes user DB, conversation DB, message DB shards, Redis for presence/session routing, Kafka for internal events, object storage/CDN for media, and search or ledger stores for optional features.

For one-to-one messages, the important invariant is persist before delivery. The client sends a message envelope with `clientMsgId`. The server checks idempotency, gets the next `serverSeq` for the conversation, writes the message and outbox event in one transaction, and ACKs. An outbox publisher writes to Kafka keyed by conversationId so consumers preserve per-conversation order. Delivery workers check Redis for recipient sessions. Online devices get WebSocket delivery; offline devices get push wake-up and later sync. ACKs are idempotent and can be coalesced.

For groups, group metadata and participant membership are versioned. Small groups can create per-recipient inbox tasks on write, which makes reads fast. Very large groups store the message once in the group stream and let recipients pull, with active members possibly receiving fan-out. Ordering is per conversation only. Duplicates are handled by client message id and by idempotent consumers. Redis is not the message store; if Redis fails, presence becomes unknown and sync still works. Kafka is not the client protocol; it decouples backend side effects like delivery, push, indexing, media processing, and metrics."

### 30-minute answer

"I’ll start with requirements: one-to-one and group messaging, offline delivery, receipts, media, voice notes, calls, status, linked devices, privacy, and abuse controls. Non-functional goals are low send ACK latency, high durability, per-conversation ordering, huge socket scale, and graceful degradation. I’ll state that this is a WhatsApp-like industry design and that private internals may differ.

The high-level architecture has clients using WebSocket for realtime, HTTPS for APIs and media, and WebRTC for calls. The Message Service owns the critical write path: authenticate, authorize, dedupe by `(senderId, clientMsgId)`, assign `serverSeq`, persist to Message DB, write an outbox event, and ACK. The outbox publishes to Kafka so DB commit and async delivery do not split-brain. Kafka topics are keyed by conversationId for ordered consumers. Delivery workers transform events into recipient-device delivery attempts. Redis stores presence and session routing with TTLs. If Redis is wrong or unavailable, we degrade to push plus sync because the durable message log is still correct.

For data, messages are partitioned by conversationId and time bucket; users by userId; groups by groupId; media by mediaId; receipts are high-water marks. Direct chats have generated conversation ids. Groups reuse the conversation stream plus membership tables with joinSeq/leftSeq or membership version. Small groups use fan-out on write, large groups use pull or hybrid, and huge receipt details are compacted. Linked devices mean encryption envelopes and delivery state may be per device, while read state can roll up per user.

Media uses object storage and CDN with upload URLs, async transcode, thumbnails, and lifecycle rules. The message contains a media reference, not raw bytes. Typing and presence are ephemeral WebSocket/Redis signals. Live location is a time-bounded stream with recent points in Redis and durable share metadata. Calls use WebSocket signaling to exchange offers, answers, and ICE candidates; media flows through WebRTC peer-to-peer when possible, TURN relay when needed, and SFU for group calls. Kafka does not carry audio/video packets.

For multi-region, I would choose user-home or conversation-home ownership initially, with async replication and explicit failover semantics. Active-active per conversation is possible but increases conflict complexity. Security includes TLS, token auth, device binding, end-to-end encrypted payloads, key rotation, signed media URLs, block lists, rate limits, and payment ledger controls if payments exist. Observability tracks send ACK latency, delivery latency, Kafka lag, socket count, Redis health, DB hot shards, duplicate rate, push success, media failures, and call setup failures. Deployment uses canaries, feature flags, backward-compatible schemas, and load shedding that drops typing before durable messages."
