## Primary interview story

> Alice sends Bob a message.

## Message state machine

<Mermaid chart={`stateDiagram-v2
    [*] --> CREATED
    CREATED --> PERSISTED: write DB
    PERSISTED --> SENT: ack to sender
    SENT --> DELIVERED: device ack
    DELIVERED --> READ: user opens
    PERSISTED --> RETRYING: delivery fail
    RETRYING --> SENT: republish/push
    RETRYING --> FAILED: exhausted
    FAILED --> DLQ: poison / manual
    DLQ --> PERSISTED: replay`} />

| UI tick | State | Meaning |
|---|---|---|
| Clock / empty | CREATED→PERSISTED | Local only / uploading |
| Single grey | SENT | Server durable |
| Double grey | DELIVERED | At least one recipient device got it |
| Double blue | READ | Recipient opened (privacy settings apply) |

## WHAT → HOW → WHY → FAILURE → SCALE

| | |
|---|---|
| **WHAT** | Durable chat with receipts |
| **HOW** | Persist → Kafka → presence-aware push |
| **WHY** | Don’t block Alice on Bob’s network |
| **FAILURE** | Retry delivery; never lose after PERSISTED |
| **SCALE** | Partition Kafka + shard DB by conversationId |

---

## Interview explanation (30 sec)

> Persist first, then async deliver. Online path is WebSocket; offline is push + sync on reconnect. Ticks are status events, not separate message bodies.

## Corner case

Alice’s phone dies after server persist but before she sees SENT → client retries with same `clientMsgId` → idempotency returns same `messageId`.
