## Redis cluster map

| Use | TTL? | Durable source of truth? |
|---|---|---|
| Presence | Yes | No — reconnect rebuilds |
| Connection registry | Yes | No |
| Idempotency accel | Hours–days | DB unique constraint too |
| Rate limit | Yes | No |
| Locks | Seconds | No |
| Cache profile | Short | SQL/NoSQL owns data |

### Do NOT permanently store in Redis alone

```text
Message bodies · chat history · payment ledger · group membership source of truth
```

## Distributed lock

<Mermaid chart={`sequenceDiagram
    participant A as Instance A
    participant R as Redis
    participant B as Instance B

    A->>R: SET lock:conv:123 NX EX 10 token=T1
    R-->>A: OK
    B->>R: SET lock:conv:123 NX ...
    R-->>B: FAIL
    A->>A: critical section
    A->>R: unlock if token=T1
`} />

### WhatsApp-like use case

Serialize **serverSeq allocation** if not using Redis `INCR` / DB sequence:

```text
lock:seq:conversation:{id}
  → read max seq → write msg with seq+1
```

Better: `INCR conversation:{id}:seq` (atomic) — **no lock needed**.

### Rules

| Do | Don't |
|---|---|
| TTL always | Infinite locks |
| Ownership token on unlock | Delete lock blindly |
| Prefer DB uniqueness / atomic ops | Lock for every message send |
| Short critical sections | Hold lock during Kafka produce + WS push |

Redlock: mention as controversial; for this design prefer single Redis primary or DB constraints for correctness-critical uniques.

---

## Interview explanation

> Redis is the hot ephemeral layer: presence, registry, rate limits, idempotency cache. Messages stay in the message store. I avoid distributed locks when an atomic counter or unique index works.

## Corner case

Lock expires mid-section → second instance enters → use fencing token / seq atomicity to stay safe.
