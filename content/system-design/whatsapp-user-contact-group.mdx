## 5. Registration / Login

<Mermaid chart={`sequenceDiagram
    participant C as Client
    participant GW as API Gateway
    participant A as Auth Service
    participant U as User DB
    participant T as Token / Session
    participant D as Device Store

    C->>GW: POST /otp/request {phone}
    GW->>A: send OTP
    A->>C: OTP via SMS provider
    C->>GW: POST /otp/verify {phone, otp, deviceId}
    GW->>A: verify
    A->>U: upsert user
    A->>D: register device
    A->>T: issue access + refresh
    T-->>C: tokens + userId`} />

| Concern | Approach |
|---|---|
| OTP | Short TTL, rate limit per phone/IP |
| Access token | JWT/session, short lived |
| Refresh | Rotating refresh, device-bound |
| Device ID | Stable per install; revoke on logout |

## 7. Create chat (1:1)

<Mermaid chart={`flowchart TD
  A[User A starts chat with B] --> CS[Conversation Service]
  CS --> IDEM[Idempotent pair key sorted userIds]
  CS --> CDB[(Conversation DB)]
  CS --> PDB[(Participant DB)]
  CS --> ID[Return conversationId]`} />

**Why stable `conversationId` matters**

```text
ordering key → Kafka partition
shard key  → Message DB
ACL key    → membership checks
unread     → counters per conversation
```

For 1:1, derive deterministic id from sorted `(userA, userB)` so retries don’t create two chats.

## 8. Create group

<Mermaid chart={`sequenceDiagram
    participant Admin
    participant GW as API Gateway
    participant GS as Group Service
    participant DB as Group + Member DB
    participant K as Kafka
    participant N as Notify / WS

    Admin->>GW: createGroup {name, members[]}
    GW->>GS: authorize
    GS->>DB: insert group + members + admin role
    GS->>K: GroupCreated
    K->>N: fan-out event
    N-->>Admin: success
    N-->>Members: WS or push "added to group"`} />

| Operation | Notes |
|---|---|
| Add/remove member | Authz admin; emit membership event |
| Promote/demote | Role update + event |
| Leave | Self remove; last admin transfer policy |
| Group photo | Media service + metadata URL |
| Permissions | Who can send / edit info / add members |

### Group corner case

Message in-flight while member removed → delivery worker re-checks membership at send time; drop or mark failed for that user.

---

## Interview explanation

> Auth binds phone + device. Contacts are a private edge list with privacy. Conversations own the durable id used for partitions. Groups are membership + roles with event fan-out.

## Scale

User/contact SQL with read replicas; group member lists cached briefly; large groups → specialized fan-out (see Group Messaging page).
