## Ordering architecture

<Mermaid chart={`flowchart TD
  C[conversationId] --> PK[Kafka partition key]
  PK --> P[Single partition]
  P --> CONS[Ordered consumer]
  CONS --> DB[(DB rows ordered by serverSeq)]`} />

### Example

```text
M1 "Hi"
M2 "How are you?"
M3 "Where are you?"

All share conversationId=C123
→ same Kafka partition
→ same consumer processes M1 then M2 then M3
→ serverSeq 1,2,3 persisted
```

| Mechanism | Role |
|---|---|
| Partition by conversationId | Per-chat Kafka order |
| serverSeq | Client-visible order even if clocks skew |
| Client timestamp | Display hint only, not source of truth |
| Single writer per conv (optional lock) | Rare; prefer seq allocator atomicity |

### Multi-device senders

Alice phone and Alice desktop both send → both hit Message Service → seq allocator (`INCR` Redis or DB atomic counter per conversation) serializes numbers.

### Out-of-order network

Device may receive M3 before M2 over flaky WS → client buffers by serverSeq and renders in order.

## Idempotency

<Mermaid chart={`flowchart TD
  CL[Client clientMsgId UUID] --> MS[Message Service]
  MS --> ST{idempotency key exists?}
  ST -->|Yes| RET[Return previous messageId]
  ST -->|No| NEW[Persist + Kafka]
  NEW --> SAVE[Save idempotency mapping TTL/long]`} />

### What if…

| Scenario | Protection |
|---|---|
| Client retries HTTP/WS | Same clientMsgId |
| Kafka redelivery | Consumer idempotent on messageId |
| Crash after process before commit | Re-process safe |
| WS reconnect replay | Dedupe by messageId on device |
| API timeout but server OK | Retry returns same result |

### Sketch

```java
String key = userId + ":" + clientMsgId;
if (!redis.setIfAbsent(key, "LOCK", Duration.ofSeconds(30))) {
    return replayFromDb(key);
}
```

Prefer durable DB unique constraint `(sender_id, client_msg_id)` as source of truth; Redis is acceleration.

---

## Interview explanation

> Ordering scope is the conversation, not the whole platform. Kafka partition key = conversationId; serverSeq is the contract. Duplicates die with clientMsgId uniqueness.

## Corner case

Hot celebrity chat → hot partition → mitigate with separate “fan-out” path / multiplexing for mega-groups (see group page).
