## The problem

A rider requests a car and expects a nearby driver to be matched quickly. Driver locations change every few seconds, so the system must handle a high write rate while serving low-latency spatial queries.

## Requirements

Rider requests, driver availability, nearby-driver search, trip lifecycle, pricing, cancellation, notifications and location tracking.

## Architecture

```text
Rider → API → Trip Service → Matching Service → Geo Index
                         |          |
                         |          +→ Driver Location Store
                         +→ Kafka → Pricing / Notifications / Analytics
```

## Geospatial matching

The matching service needs an index optimized for nearby queries. A geohash, S2 cell or another spatial partition can map coordinates into regions. The system searches the driver's current cell and neighboring cells rather than scanning every driver.

## Trip state

```text
REQUESTED → MATCHING → DRIVER_ASSIGNED → ARRIVING → IN_TRIP → COMPLETED
                                      ↘ CANCELLED
```

State transitions must be guarded against races. A driver should not be assigned to two trips simultaneously.

## Concurrency

Matching can use a short-lived reservation or distributed lock around driver assignment, but the strongest protection should still be an atomic business-state transition in the authoritative store.

## Scaling

Location updates are high-volume and can be separated from durable trip state. Hot geographic regions may require adaptive partitioning. Kafka can distribute location-derived events to consumers while a low-latency location store serves current positions.

## Reliability

If location updates stop, mark a driver stale rather than assuming they remain available. If a matching worker fails, another worker can retry based on the trip state. Notifications are asynchronous and should be idempotent.

## Trade-offs

| Decision | Benefit | Cost |
|---|---|---|
| Spatial index | Fast nearby search | Rebalancing complexity |
| Event streaming | Decoupling | Eventual updates |
| State machine | Correct lifecycle | More explicit modeling |
| Short reservation | Prevents double assignment | Lock contention |

## Staff-level discussion

Separate current location from durable trip history. Current location is rapidly changing derived state; trip state and financial outcomes need stronger correctness guarantees.
