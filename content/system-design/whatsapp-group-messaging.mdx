---

## Fan-out on write

```text
1 message → N per-user inboxes / push tasks
```

| Pros | Cons |
|---|---|
| Fast reads | Write amplification |
| Easy unread | Painful for huge N |

**Best for:** normal groups (&lt; few hundred / thousand).

---

## Fan-out on read

```text
Store one copy on group timeline
Members pull / sync new serverSeq
```

| Pros | Cons |
|---|---|
| Cheap writes | Reads heavier |
| Scales celebrity | Harder push fan-out |

**Best for:** very large / broadcast-like audiences.

---

## Hybrid recommendation

```text
Small/medium groups → fan-out on write (async workers)
Mega groups / channels → fan-out on read + selective push
```

---

## Hot partitions

Celebrity groupId → one Kafka partition melts.

Mitigations:

```text
Separate channel product
Shuffle keys for notify topic (accept weaker order for notifies)
Dedicated consumer pool
Rate limit senders
```

Chat order still enforced by serverSeq in DB even if notify parallelized.

## Interview explanation

> Persist once, fan-out asynchronously. Use write fan-out for normal groups; read fan-out for huge audiences. Always re-check membership at delivery.
