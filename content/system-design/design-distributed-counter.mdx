### Mental model

```text
Client click -> idempotency gate -> sharded atomic INCR -> ACK UX -> async delta -> durable snapshot
GET = sum(shards)  OR  snapshot + known lag
```

WHAT: a counter is a **high-QPS write-optimized number** with an explicit consistency contract.  
HOW: avoid a single DB row; use sharded atomic increments on Redis (or equivalent), then async aggregation for durability and analytics.  
WHY: celebrity posts create hot keys; retries create double-counts; Redis alone is not a permanent ledger.

### Interview promise

```text
I will never put viral likes on a single UPDATE likes = likes + 1 row.
Hot path: sharded Redis INCR. Durable path: Kafka deltas → aggregator snapshot.
LIKE is at-most-once per user×resource. VIEW can be many increments.
```

| Invariant | Why it matters |
|---|---|
| Hot path is sharded atomic INCR | Single row / single Redis key becomes a hotspot. |
| LIKE is at-most-once per user×resource | Double-click and retries must not inflate counts. |
| ACK UX fast; snapshot can lag | Product usually accepts short display lag. |
| Rebuild path exists | Redis is cache-like; events/DB restore truth. |
| Exact vs approximate is a product call | Money ≠ likes ≠ unique viewers. |

## The interview story (viral post)

A celebrity posts a photo. Within minutes, **200K likes/minute** hit one `postId`. If your design is:

```sql
UPDATE posts SET like_count = like_count + 1 WHERE id = ?
```

that single row becomes a write lock hotspot and the database melts.

Better story:

Alice taps Like. The Counter API checks she has not already liked this post (`userId × postId`). It hashes Alice into shard `7` of 16 and atomically increments `counter:post123:shard:7`. The API returns 200 immediately so the heart fills in the UI. Asynchronously, an outbox publishes `CounterDeltaEvent` to Kafka. An Aggregator merges deltas into a durable snapshot for analytics and Redis rebuild. Bob's GET for the count sums all shards (or reads a slightly lagged snapshot — you state which).

## Requirements and estimation

### Functional requirements

| Requirement | Notes |
|---|---|
| Increment | `+delta` (usually 1) for a `resourceId` |
| Decrement / unlike | Optional; never go below zero |
| Read current value | Fast GET for UI |
| Like uniqueness | At most one like per user per resource |
| View counting | Many increments; optional unique viewers |
| Batch / admin reset | Rare ops with audit |

### Non-functional requirements

| NFR | Talking point |
|---|---|
| Latency | p99 incr ACK &lt; 20–50ms in-region |
| Throughput | 100K–1M+ incr/sec on viral keys |
| Durability | Survive Redis node loss via rebuild |
| Consistency | Exact likes; eventual display OK |
| Cost | Cheap hot path; batch durable writes |

### REST API endpoints

Implemented by the Spring Boot demo (`spring-distributed-counter-demo/`).

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/counters/{resourceId}/increment` | Like / view increment |
| `GET` | `/api/v1/counters/{resourceId}` | Current value (shard sum) |
| `GET` | `/api/v1/counters/{resourceId}/shards` | Per-shard breakdown |

```http
POST /api/v1/counters/post-123/increment HTTP/1.1
Content-Type: application/json
X-User-Id: alice
Idempotency-Key: alice-like-post-123

{
  "delta": 1,
  "action": "LIKE",
  "clientRequestId": "alice-like-post-123"
}
```

```json
{
  "resourceId": "post-123",
  "value": 42,
  "accepted": true,
  "duplicate": false,
  "shard": 7
}
```

Retry with the same idempotency key / like uniqueness returns `duplicate: true` and **does not** increase the count.

## High-level architecture

```text
Client → API Gateway → Counter Service
                           |-- Idempotency store (LIKE seen-set)
                           |-- Sharded Redis INCR
                           |-- Outbox → Kafka CounterDelta
                                    → Aggregator → Snapshot DB
GET ← sum(shards)  or  snapshot (+ lag)
```

### Why each piece exists

| Component | Role |
|---|---|
| Counter Service | Validate, idempotency, pick shard, ACK |
| Sharded Redis | Atomic hot-path INCR without single-key hotspot |
| Idempotency / seen-set | Prevent double-like and safe retries |
| Outbox + Kafka | Reliable async durability / analytics |
| Aggregator + Snapshot | Rebuild source and reporting |

### Consistency modes (say one)

| Mode | GET behavior | Use |
|---|---|---|
| **Shard sum** | Read all N shard keys and sum | Exact, more Redis RTTs |
| **Snapshot** | Read aggregated DB/Redis total | Faster, short lag |
| **Hybrid** | Snapshot + recent local buffer | UX smooth |

## Exact likes vs approximate views

| Use case | Technique | Notes |
|---|---|---|
| Exact likes | INCR + unique `(userId, resourceId)` | Product truth |
| Exact play count | Sharded INCR | Accept eventual display |
| Unique viewers | HyperLogLog / bloom | ~1% error OK |
| Ranking / trends | Approximate + periodic exact | Cost control |

**Staff line:** "I will not use HLL for bank balances or like counts that users can dispute; I will use HLL for unique impression estimates."

## Hot-key mitigations

| Technique | How | Trade-off |
|---|---|---|
| Key sharding | `counter:{id}:shard:{i}` | GET must sum N keys |
| Local buffer | Pod accumulates 50–100ms then flush | Crash loses tiny buffer unless careful |
| Hierarchical | Edge regional counters + global merge | Cross-region lag |
| Read snapshot | Cache total for feed rendering | Stale by design |
| Write shedding | Drop VIEW under extreme load | Never drop payment; product policy |

### LLD sequence — LIKE increment

```text
1. Controller binds DTO + X-User-Id + Idempotency-Key
2. Service: if action=LIKE → IdempotencyStore.tryAcquire(user, resource)
   - false → return current value, duplicate=true
3. shard = ShardSelector.select(userId or requestId, shardCount)
4. CounterRepository.incrShard(resourceId, shard, delta)
5. Outbox save + DeltaPublisher.publish(CounterDeltaEvent)
6. Return { value: sumShards or approximate, accepted: true }
```

### Key data structures

| Structure | Key | Value |
|---|---|---|
| Shard counter | `counter:{resourceId}:shard:{i}` | long |
| Like seen-set | `liked:{resourceId}` or pair key | set / bitmap / DB unique |
| Idempotency | `idem:{clientRequestId}` | result stub TTL |
| Snapshot | `snapshot:{resourceId}` | long + updatedAt |
| Outbox | `outboxId` | serialized delta |

### Core algorithms (interview whiteboard)

**Shard pick**

```text
shard = hash(userId XOR resourceId) % N
```

**INCR (atomic)**

```text
REDIS: INCRBY counter:{id}:shard:{s} delta
```

**GET exact**

```text
total = 0
for i in 0..N-1:
  total += GET counter:{id}:shard:{i}
return total
```

**Unlike**

```text
if remove from seen-set succeeded:
  DECRBY same shard (or any shard) by 1
  clamp at 0 in aggregator if needed
```

### REST controller (`counter-api`)

```java
@RestController
@RequestMapping("/api/v1/counters")
public class CounterController {
  @PostMapping("/{resourceId}/increment")
  public IncrementCounterResponse increment(
      @PathVariable String resourceId,
      @RequestHeader(name = "X-User-Id", required = false) String userId,
      @RequestHeader(name = "Idempotency-Key", required = false) String idempotencyKey,
      @RequestBody IncrementCounterRequest request) {
    return counterService.increment(resourceId, request, userId, idempotencyKey);
  }

  @GetMapping("/{resourceId}")
  public CounterValueResponse get(@PathVariable String resourceId) {
    return counterService.get(resourceId); // SHARD_SUM
  }

  @GetMapping("/{resourceId}/shards")
  public ShardBreakdownResponse shards(@PathVariable String resourceId) {
    return counterService.shards(resourceId);
  }
}
```

### Increment service (idempotency → shard INCR → outbox)

```java
IdempotencyDecision decision = idempotencyStore.reserveIfFirst(
    resourceId, action, userId, request.clientRequestId(), idempotencyKey);
if (!decision.firstWrite()) {
  return new IncrementCounterResponse(resourceId, counterStore.sum(resourceId),
      false, -1, null, decision.key().orElse(null), "SHARD_SUM");
}

ShardKey shardKey = counterStore.chooseShard(resourceId, stableShardHint(...));
counterStore.increment(shardKey, delta);          // hot path first
outboxPublisher.publish(new CounterDeltaEvent(...)); // then async durability
return new IncrementCounterResponse(resourceId, counterStore.sum(resourceId),
    true, shardKey.shard(), ...);
```

### Map demo → HLD invariants

| Invariant | Code |
|---|---|
| Sharded INCR | `ShardedCounterStore.increment` + `chooseShard` |
| LIKE at-most-once | `IdempotencyStore.reserveIfFirst` |
| Persist then event | incr then `OutboxPublisher.publish` |
| GET exact | `counterStore.sum` → `SHARD_SUM` |
| Async durability | `CounterDeltaEvent` → aggregator `SnapshotStore` |

## Multi-region, failures, observability

### Multi-region

| Pattern | Notes |
|---|---|
| Sticky region | User likes in home region shards |
| Active-active | Regional shards + global Kafka merge; accept lag |
| CRDT G-Counter | Math for mergeable increments (Staff bonus) |

### What-if Q&A

| Question | Answer |
|---|---|
| Single DB row? | No for viral hot path |
| Redis loses data? | Rebuild from snapshot + Kafka replay |
| Kafka lag? | Shard sum still correct for GET |
| Double-click? | Idempotency + LIKE uniqueness |
| Unlike? | Remove seen + DECR; never negative |
| Unique views? | HLL; say error bound |
| Rate limiter vs counter? | Limiter decides allow/deny; counter stores magnitude |
| Clock skew? | Don't use wall clock for uniqueness |
| Shard imbalance? | Rehash / raise N / salt by requestId |
| Money counters? | Strong ledger, not this design |

### Metrics

| Metric | Alert |
|---|---|
| incr latency p99 | Hot shard / Redis |
| duplicate rate | Client retry storms |
| Kafka lag | Snapshot staleness |
| shard skew | Rebalance N |
| rebuild duration | DR readiness |

## 5 / 15 / 30 minute spoken answers

### 5-minute

"I'll design a distributed counter for likes and views. The naive `UPDATE likes = likes + 1` on one row dies under viral QPS. Hot path is sharded Redis `INCR` on `counter:{id}:shard:{i}`. For likes I enforce at-most-once per user and resource with an idempotency store. The API ACKs immediately after the shard increment, then publishes a delta through an outbox to Kafka. An aggregator builds a durable snapshot for rebuild and analytics. GET returns the sum of shards for an exact read, or a snapshot if we accept short lag. Views can use plain increments; unique viewers can use HyperLogLog."

Add: REST shapes, shard selection hash, local buffer flush, exact vs approximate product call, fail/rebuild if Redis is lost, Kafka lag does not corrupt shard-sum GET, unlike via DECR + seen-set removal, difference from rate limiter.

## Staff-level closing

Hot counters are a **write-amplification and hotspot** problem first, a storage problem second. Name the consistency contract, shard the hot key, make likes idempotent, ACK fast, and always have a rebuild story. Point to the runnable Spring modules when asked "how would you implement this?"
