## 1. Requirements

### Functional

| Feature | Must support |
|---|---|
| 1:1 chat | Send/receive, media, reply |
| Groups | Create, admin, members, messages |
| Receipts | SENT / DELIVERED / READ |
| Presence | Online, last seen (privacy-aware) |
| Offline | Deliver when user returns |
| Multi-device | Phone + linked desktop/web |
| Media | Image, video, doc, voice |
| Calls | Audio, video, group (signalling + WebRTC) |
| Status | 24h ephemeral stories |
| Search | Local + server message search |

### Non-functional

| NFR | Target thinking |
|---|---|
| Latency | p99 send→online deliver &lt; few hundred ms regionally |
| Durability | Message not lost after ACK from server |
| Availability | Chat path survives single AZ / node loss |
| Scale | 100M+ DAU, millions concurrent WS |
| Consistency | Per-conversation order; status eventual |
| Security | TLS everywhere; E2EE changes payload visibility |

### Capacity sketch (say in interview)

```text
100M DAU × 40 msgs/day ≈ 4B msgs/day
≈ 46K msg/s average → design for 5–10× peak
WebSocket: concurrent online ≈ 10–20% DAU → tens of millions connections
→ many gateway nodes × ~50–100k connections/node (hardware dependent)
```

### Why this shape (not the naive one)

| Choice | Why |
|---|---|
| Separate WebSocket fleet | Long-lived connections ≠ short HTTPS |
| Message Service persists **before** fan-out | Durability first |
| Kafka after persist | Async delivery / notify / analytics without blocking sender |
| Redis for presence | Hot, TTL, not durable source of truth |
| Object storage for media | Binaries ≠ DB rows ≠ Kafka payloads |
| Conversation Service | Stable `conversationId` for ordering & sharding |

<Mermaid chart={`flowchart LR
  C[Client] -->|HTTPS REST| API[API Gateway]

  C -->|WebRTC media| P2P[Peer / SFU]
  API --> SVC[Services]

  SVC -->|Kafka protocol| K[Kafka]

| Protocol | Use for | Do NOT use for |
|---|---|---|
| HTTPS / REST | Login, OTP, profile, create group, history, media URL, search, link device | Realtime chat pump |
| WebSocket | Messages, typing, presence, ACK, group events | Large media bytes |
| HTTP/2 or HTTP/3 | API efficiency, multiplexed uploads | Replacing WS semantics |
| WebRTC | Audio/video media | Chat persistence |
| TCP | Under WS / Kafka clients | App-level chat API |
| UDP | WebRTC media (typically) | Guaranteed chat delivery alone |
| Kafka | Internal events | Direct phone↔phone |

## Interview explanation (45 sec)

> I split control-plane HTTPS APIs from data-plane WebSockets. Message Service is the source of truth for chat: persist then publish. Kafka fans out to delivery and notification workers. Presence lives in Redis with TTL. Media bypasses Kafka via S3/CDN. Calls leave the messaging path and use WebRTC.

## Corner case

WebSocket LB without sticky sessions + no connection registry → cannot find which node holds Bob → need Redis `userId → connectionId/serverId`.

## Scale

Gateway nodes horizontal; Kafka partitions; message shards by conversation; Redis cluster; CDN for media.
