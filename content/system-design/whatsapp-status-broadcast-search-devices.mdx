## Broadcast vs group

<Mermaid chart={`flowchart TD
  S[Sender] --> BC[Broadcast Service]
  BC --> LIST[Recipient list]
  LIST --> Q[Per-user message enqueue]
  Q --> U1[User 1 chat]
  Q --> U2[User 2 chat]
  Q --> UN[User N chat]`} />

| | Group | Broadcast |
|---|---|---|
| Shared history | Yes | No — separate 1:1 copies |
| Recipients see each other | Yes | No |
| Fan-out | Membership-based | Explicit list explode |

Large lists → chunked workers; rate limit; avoid one giant Kafka message.

## Search

<Mermaid chart={`flowchart LR
  C[Client] --> API[Search API]
  API --> S[Search Service]
  S --> IDX[(Search Index)]
  IDX --> IDS[messageIds]
  IDS --> MDB[(Message DB fetch)]`} />

| Concern | Note |
|---|---|
| Indexing | Async from message.created |
| Consistency | Near-realtime eventual |
| Delete | Tombstone in index |
| Privacy | Filter by participant ACL |
| E2EE | Server search limited if ciphertext only; often device-local |

## Interview explanation

> Status is ephemeral media+TTL. Broadcast explodes into 1:1 sends. Search is async index + ACL. Linked devices are first-class sessions synced by serverSeq.
