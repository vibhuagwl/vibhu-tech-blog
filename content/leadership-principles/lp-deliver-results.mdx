## Principle

Leaders focus on the key inputs for their business and deliver them with the right quality and in a timely fashion. Despite setbacks, they rise to the occasion and never settle.

## Primary STAR — Pack of quantified deliveries

Amazon loves a crisp results narrative. Bundle honestly:

| Result | Where | Inputs you owned |
|---|---|---|
| API latency **−60%**, throughput **+70%**, batch **~80%** faster | PayPal | API/query/cache redesign |
| Report time **−90%** | PayPal | Kafka real-time pipelines |
| **$1M+/yr** saved | PayPal | Splunk → custom analytics |
| **99.9%** availability | PayPal | Event-driven microservices |
| Onboarding **+35%** faster | JPMC | Participant/cash/SWIFT APIs |
| Recovery **−50%** | JPMC | Kafka DLQ Replay Tool |
| Release confidence ↑ | JPMC | Playwright UI+API regression |

**Sample answer:**

**Situation:** At PayPal, merchants and internal platforms felt slow APIs and sluggish reports while we modernized.

**Task:** Deliver measurable performance and reporting outcomes, not only migration checkboxes.

**Action:** Redesigned APIs/queries/caching; implemented Kafka pipelines for logging/analytics; held reliability bar through the migration.

**Result:** Numbers above; rose through setbacks (rebalances, schema issues) with dive-deep fixes.

## Backup — Deliver under regulatory pressure (UBS Brexit)

Owned multithreaded processing for high-volume payloads and end-to-end releases with change management — on-time compliance functionality with zero-disruption release practices.

## Common questions

### Q1. Tell me about a missed deadline.

**A:** Tax UAT found edge-case error handling gaps. I renegotiated scope: ship core calculation path with feature flag; follow with SQS error taxonomy hardening in days, not silent slip. Communicated early; protected customer-facing accuracy.

### Q2. How do you choose key inputs?

**A:** For payments: correctness SLIs, lag/DLQ, p99 on onboarding APIs, escaped defects. Vanity story points are not inputs.

### Q3. Deliver results when dependencies fail?

**A:** Parallelize: mock/contract tests, SQS buffering, clear escalation; keep team shipping testable increments.


## Kafka case bank (reuse across follow-ups)

Use these concrete cases when the interviewer digs into Kafka after your story.

| Case | What happened | What you owned | Result |
|---|---|---|---|
| Consumer lag spike | Downstream HSBC/SWIFT validation slowed; lag grew on payment topic | Tuned concurrency, partitioned hot keys, added lag alerts + backpressure | Restored SLA without data loss |
| Poison message / DLQ | Bad SWIFT payload blocked partition processing | Built DLQ + bulk replay tool with account/SWIFT validation | Incident recovery time **−50%** |
| Duplicate events | Retries after broker blip caused duplicate tax/payment side effects | Idempotency keys + dedupe store; exactly-once *effect* design | Zero double-posting in replay drills |
| Schema / contract break | Producer shipped incompatible event | Compatibility checks in CI, consumer defensive parsing, canary topic | Caught before broad blast radius |
| Rebalance storm | Rolling deploy caused frequent rebalances | `max.poll.interval`, sticky assignor, drain-before-shutdown | Stable throughput during deploys |
| Out-of-order cash events | Same account events across partitions | Key by account/cash-line; ordering within key | Correct reconciliation order |
| Analytics pipeline | Merchant reports took hours from batch DB pulls | Real-time Kafka logging → parallel consumers | Report generation **−90%** time (PayPal) |
| Observability gap | Hard to prove “message landed then failed downstream” | Correlation IDs, lag/DLQ dashboards (Splunk/CloudWatch) | Faster RCA, fewer finger-pointing loops |
