## Principle

Speed matters in business. Many decisions and actions are reversible and do not need extensive study. We value calculated risk taking.

## Primary STAR — Act during Kafka payment recovery

**Situation:** DLQ depth and lag threatened reconciliation SLAs; waiting for a perfect multi-quarter platform project was not an option.

**Task:** Reduce customer/ops impact quickly while moving toward a durable fix.

**Action:**
1. Two-way door now: guarded manual replay for critical backlog with dual control.
2. Parallel path: implement DLQ Replay Tool with validation (one-way door for process change, but shipped iteratively).
3. Communicated risk clearly to stakeholders; time-boxed spikes.
4. Instrumented as we went so action produced learning.

**Result:** Recovery time **−50%**; stopped the bleeding without normalizing unsafe republish.

## Backup — Ship regression framework incrementally

Started with critical onboarding/payment API smokes in Playwright, expanded coverage once the feedback loop proved value — action over waiting for a perfect suite.

## Common questions

### Q1. Tell me about a calculated risk.

**A:** Enabling higher consumer concurrency during lag — risk of duplicate side effects. Mitigated with idempotency keys first, then scaled concurrency.

### Q2. When did you wait instead of acting?

**A:** Schema-incompatible producer change: I blocked rollout (one-way door) until compatibility tests passed. Bias for action ≠ reckless on data contracts.

### Q3. Example of a reversible decision.

**A:** Feature-flagging a new validation rule; toggle off if false positives spike in UAT.


## Kafka case bank (reuse across follow-ups)

Use these concrete cases when the interviewer digs into Kafka after your story.

| Case | What happened | What you owned | Result |
|---|---|---|---|
| Consumer lag spike | Downstream HSBC/SWIFT validation slowed; lag grew on payment topic | Tuned concurrency, partitioned hot keys, added lag alerts + backpressure | Restored SLA without data loss |
| Poison message / DLQ | Bad SWIFT payload blocked partition processing | Built DLQ + bulk replay tool with account/SWIFT validation | Incident recovery time **−50%** |
| Duplicate events | Retries after broker blip caused duplicate tax/payment side effects | Idempotency keys + dedupe store; exactly-once *effect* design | Zero double-posting in replay drills |
| Schema / contract break | Producer shipped incompatible event | Compatibility checks in CI, consumer defensive parsing, canary topic | Caught before broad blast radius |
| Rebalance storm | Rolling deploy caused frequent rebalances | `max.poll.interval`, sticky assignor, drain-before-shutdown | Stable throughput during deploys |
| Out-of-order cash events | Same account events across partitions | Key by account/cash-line; ordering within key | Correct reconciliation order |
| Analytics pipeline | Merchant reports took hours from batch DB pulls | Real-time Kafka logging → parallel consumers | Report generation **−90%** time (PayPal) |
| Observability gap | Hard to prove “message landed then failed downstream” | Correlation IDs, lag/DLQ dashboards (Splunk/CloudWatch) | Faster RCA, fewer finger-pointing loops |
