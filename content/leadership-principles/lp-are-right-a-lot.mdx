## Principle

Leaders are right a lot. They have strong judgment and good instincts. They seek diverse perspectives and work to disconfirm their beliefs.

## Interviewer signals

- You show **judgment**, not luck
- You sought disconfirming data
- You changed your mind when evidence demanded it
- You explain *why* the bet was correct

## Primary STAR — Performance redesign bets (PayPal)

**Q: Tell me about a time your judgment was proven right.**

**Situation:** APIs and batch jobs were missing latency/throughput targets; opinions differed (scale hardware vs fix queries vs cache vs rewrite).

**Task:** Choose the highest-leverage path for Java/Spring microservices under real traffic.

**Action:**
1. Measured: p99 by endpoint, slow query log, cache hit ratio, batch stage timings.
2. Disconfirmed “just add pods” — CPU was fine; wait time was DB and chatty APIs.
3. Redesigned APIs, queries, and caching deliberately.
4. Validated with load tests before broad rollout.

**Result:** API response **−60%**, throughput **+70%**, batch **~80%** faster.

## Backup STAR — Monolith to microservices on GCP

**Judgment:** Carve services along transactional boundaries and event seams (Kafka), not along team org charts alone.  
**Result:** Faster release cycles, better scalability, lower operational complexity over time.

## When you were wrong (must-have story)

**Q: Tell me about a time you were wrong.**

**A:** I initially favored more partitions to fix lag. Dive-deep showed a hot key and slow SWIFT validation. Extra partitions would not fix per-key ordering bottlenecks. I reversed course: optimized validation path, consumer concurrency, and keying strategy; lag recovered. Seeking disconfirming metrics is the LP.

## Kafka case bank (reuse across follow-ups)

Use these concrete cases when the interviewer digs into Kafka after your story.

| Case | What happened | What you owned | Result |
|---|---|---|---|
| Consumer lag spike | Downstream HSBC/SWIFT validation slowed; lag grew on payment topic | Tuned concurrency, partitioned hot keys, added lag alerts + backpressure | Restored SLA without data loss |
| Poison message / DLQ | Bad SWIFT payload blocked partition processing | Built DLQ + bulk replay tool with account/SWIFT validation | Incident recovery time **−50%** |
| Duplicate events | Retries after broker blip caused duplicate tax/payment side effects | Idempotency keys + dedupe store; exactly-once *effect* design | Zero double-posting in replay drills |
| Schema / contract break | Producer shipped incompatible event | Compatibility checks in CI, consumer defensive parsing, canary topic | Caught before broad blast radius |
| Rebalance storm | Rolling deploy caused frequent rebalances | `max.poll.interval`, sticky assignor, drain-before-shutdown | Stable throughput during deploys |
| Out-of-order cash events | Same account events across partitions | Key by account/cash-line; ordering within key | Correct reconciliation order |
| Analytics pipeline | Merchant reports took hours from batch DB pulls | Real-time Kafka logging → parallel consumers | Report generation **−90%** time (PayPal) |
| Observability gap | Hard to prove “message landed then failed downstream” | Correlation IDs, lag/DLQ dashboards (Splunk/CloudWatch) | Faster RCA, fewer finger-pointing loops |


| Decision | Alternatives | Why chosen |
|---|---|---|
| Idempotent consumer + dedupe | “Enable EOS and relax app checks” | Need exactly-once *business effect* across DB+side effects |
| DLQ + validated replay | Infinite retries | Poison messages must not block partition forever |
| Key by account | Random key for max parallelism | Ordering/reconciliation correctness > raw fanout |

## Common questions

### Q1. How do you seek diverse perspectives?

**A:** Design reviews with API, data, and ops voices; write a one-pager with options and risks; ask juniors to critique — they spot complexity I normalize.

### Q2. Walk me through a technical decision under uncertainty.

**A:** Tax async via SQS vs synchronous Deloitte calls — uncertainty on latency spikes. Chose async with explicit error handling and visibility for admins; validated in UAT with failure injection.
