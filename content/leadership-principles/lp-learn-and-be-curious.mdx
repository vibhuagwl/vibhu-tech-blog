## Principle

Leaders are never done learning and always seek to improve themselves. They are curious about new possibilities and act to explore them.

## Primary STAR — Learning Terraform / IaC while delivering (JPMorgan)

**Situation:** Microservices needed consistent AWS deployments; I was stronger in app code than infra-as-code.

**Task:** Become effective at Terraform practices without blocking delivery.

**Action:** Pairing with platform engineers, small PRs for ECS/service wiring, translating app needs (SQS, Redis, ALB) into modules, documenting what the app team must own vs platform.

**Result:** Stronger deployment automation and environment consistency; I could review infra changes that affected reliability.

## Backup — Kafka depth from incidents

Curiosity driven by production: consumer rebalances, DLQ taxonomy, ordering, idempotency — turned into the Replay Tool and team teaching sessions.

## Backup — AI / LLM curiosity

Explored RAG, agentic patterns, MCP, Spring AI, and AI-assisted coding (Copilot/Cursor) to accelerate delivery and documentation — without putting unverified AI output into money paths.

## Common questions

### Q1. What have you learned recently that changed how you work?

**A:** Treating DLQ as a product surface (UX for ops, validation, metrics), not a dump topic. It changed how I design every Kafka consumer.

### Q2. How do you learn without hurting delivery?

**A:** Spike in a branch with a time-box; productionize only after a measurable win (e.g., replay time). Share learnings in architecture forums.

### Q3. Tell me about exploring a technology that you did not use.

**A:** Evaluated heavier workflow engines for tax errors; learned enough BPMN trade-offs to choose simpler SQS+replay for the dominant cases.


## Kafka case bank (reuse across follow-ups)

Use these concrete cases when the interviewer digs into Kafka after your story.

| Case | What happened | What you owned | Result |
|---|---|---|---|
| Consumer lag spike | Downstream HSBC/SWIFT validation slowed; lag grew on payment topic | Tuned concurrency, partitioned hot keys, added lag alerts + backpressure | Restored SLA without data loss |
| Poison message / DLQ | Bad SWIFT payload blocked partition processing | Built DLQ + bulk replay tool with account/SWIFT validation | Incident recovery time **−50%** |
| Duplicate events | Retries after broker blip caused duplicate tax/payment side effects | Idempotency keys + dedupe store; exactly-once *effect* design | Zero double-posting in replay drills |
| Schema / contract break | Producer shipped incompatible event | Compatibility checks in CI, consumer defensive parsing, canary topic | Caught before broad blast radius |
| Rebalance storm | Rolling deploy caused frequent rebalances | `max.poll.interval`, sticky assignor, drain-before-shutdown | Stable throughput during deploys |
| Out-of-order cash events | Same account events across partitions | Key by account/cash-line; ordering within key | Correct reconciliation order |
| Analytics pipeline | Merchant reports took hours from batch DB pulls | Real-time Kafka logging → parallel consumers | Report generation **−90%** time (PayPal) |
| Observability gap | Hard to prove “message landed then failed downstream” | Correlation IDs, lag/DLQ dashboards (Splunk/CloudWatch) | Faster RCA, fewer finger-pointing loops |
