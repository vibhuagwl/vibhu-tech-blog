## What this section is for

Real-Time Issues is the production incident, large-data processing, Principal interview bank, **API Integration & Frameworks**, **Aurora PostgreSQL**, **Oracle database**, **Lead Experience**, and **Java migration** (honest Java 11→17 upgrade framing) section of this interview hub.

It is built for Staff, Principal, and architect interviews where the interviewer does not want a library answer.

They want to know how you behave when the pager is loud, the dashboard is red, leadership is asking for an ETA, and every restart might make the blast radius worse.

The focus is Java and Spring Boot services backed by PostgreSQL, Kafka, and external APIs.

The tone is intentionally operational.

You should be able to say:

- what you check first
- what you refuse to guess
- how you separate mitigation from RCA
- when you restart and when you do not
- how you read JVM evidence
- how you protect downstream systems
- how you communicate uncertainty without losing control

The goal is not to memorize incident trivia.

The goal is to build an incident narrative that sounds like someone who has carried production ownership for decades.

## How to answer Real-Time Issues questions

A weak answer starts with a fix.

A strong answer starts with containment and evidence.

The Principal answer has this shape:

```text
1. Confirm customer impact and blast radius.
2. Check whether the symptom is one instance, one dependency, one shard, one topic, or the full fleet.
3. Protect the system from cascading failure.
4. Capture evidence before destructive action if safe.
5. Mitigate with the smallest safe action.
6. Keep communication crisp.
7. Perform RCA after stabilization.
8. Convert the RCA into controls, not just notes.
```

That sequence matters.

You are not rewarded for knowing `jstack` if you let a retry storm take down PostgreSQL while you are collecting dumps.

You are not rewarded for restarting every pod if the new pods immediately stampede the same locked database row.

You are not rewarded for finding the root cause after the customer-facing incident was avoidably extended.

## Interview stance

When asked, "A thread has been running for one hour. Is it stuck?"

Do not say yes.

Say:

> Not from duration alone. I need to know thread state, CPU usage, progress indicators, request age, lock ownership, downstream waits, pool metrics, and whether repeated dumps show the same stack without progress.

That answer shows maturity.

Long duration can be normal:

- batch export
- large report generation
- Kafka replay
- backfill
- schema migration support task
- checksum verification
- legitimate PostgreSQL query
- slow but bounded remote call

Long duration can also be bad:

- infinite loop
- deadlock
- lock convoy
- waiting forever on `Future.get`
- socket read without timeout
- connection pool starvation
- thread pool exhaustion
- PostgreSQL lock wait
- Kafka consumer blocked on downstream dependency

The difference is evidence.

## The production incident vocabulary

Use precise words.

| Word | Production meaning |
|---|---|
| Symptom | What users or monitors observe |
| Signal | Metric, log, trace, dump, or event that supports a hypothesis |
| Blast radius | Which customers, regions, shards, topics, or APIs are affected |
| Saturation | A finite resource is full or near full |
| Contention | Multiple actors are fighting for a shared resource |
| Backpressure | A system intentionally slows producers or callers |
| Brownout | Partial degradation instead of full outage |
| Mitigation | Action that reduces current impact |
| RCA | Explanation of why the incident happened and escaped controls |
| Corrective action | Engineering change that prevents recurrence or improves detection |

In Staff and Principal interviews, the vocabulary is a proxy for operating discipline.

## What makes Real-Time Issues different from system design

System design often starts from a blank page.

Incident response starts from a running system with users already affected.

You inherit:

- partial telemetry
- stale runbooks
- incomplete deploy context
- uncertain ownership
- multiple plausible causes
- pressure to act quickly
- risk that the mitigation is harmful

Your job is to make progress without pretending certainty.

## Java and Spring Boot focus

The guides assume common production stacks:

- Java 17 or 21
- Spring Boot services
- embedded Tomcat or Jetty
- HikariCP
- PostgreSQL
- Kafka producers and consumers
- RestTemplate, WebClient, OkHttp, or Apache HttpClient
- Micrometer, Prometheus, Grafana
- OpenTelemetry or distributed tracing
- Kubernetes or similar orchestration

The exact framework is less important than the failure pattern.

A bounded timeout is still mandatory.

A pool can still saturate.

A lock can still deadlock.

A retry can still multiply load.

A restart can still make recovery worse.

## PostgreSQL and Kafka focus

Many "stuck thread" incidents are not JVM bugs.

They are Java threads faithfully waiting on:

- a PostgreSQL row lock
- a slow query plan
- a leaked JDBC connection
- a saturated HikariCP pool
- a Kafka consumer handler blocked on a downstream call
- an external API socket read with no deadline
- an internal executor queue that never drains

The JVM shows the symptom.

PostgreSQL, Kafka, and dependency telemetry often explain the cause.

## The on-call hierarchy of concerns

During an incident, sequence your attention.

| Priority | Question |
|---:|---|
| 1 | Are users failing, slow, or receiving incorrect results? |
| 2 | Is the blast radius growing? |
| 3 | Is there an active cascade into PostgreSQL, Kafka, or another service? |
| 4 | Can we shed, throttle, disable, or route traffic safely? |
| 5 | Can we capture enough evidence before restart? |
| 6 | Is rollback safer than restart? |
| 7 | What is the next update to stakeholders? |
| 8 | What evidence do we need for RCA after impact is reduced? |

This is the voice interviewers expect from someone who has been responsible for production.

## What not to do in the interview

Avoid these answers:

- "I will just restart the server."
- "RUNNABLE means it is using CPU."
- "One-hour thread means deadlock."
- "Kafka is healthy, so consumers are fine."
- "The database is up, so it is not the database."
- "Timeouts are optional because the provider is reliable."
- "Retries will fix the dependency."
- "Thread dump is only for JVM engineers."

Each one is a real production trap.

## The five-minute stuck-thread answer

Use this if the interviewer asks for a quick response:

```text
I would first confirm impact and scope: affected endpoints, instances, p95 and p99 latency, error rate, saturation, and whether this is one thread or systemic.
Then I would check JVM metrics, request pool metrics, HikariCP, PostgreSQL wait events, Kafka lag, external dependency latency, and recent deploys.
If safe, I would capture three thread dumps around 10 seconds apart and correlate them with CPU, GC, and dependency dashboards.
I would protect the system from cascades using timeouts, circuit breakers, traffic shedding, pausing consumers, or rollback depending on the blast radius.
I would restart only if the instance is wedged, the blast radius is contained, and I have enough evidence or the customer impact requires it.
RCA comes after mitigation: root cause, missing guardrail, detection gap, and corrective actions.
```

## The twenty-minute stuck-thread answer

Use this when the interviewer wants depth.

Walk the stack:

1. User impact and SLO burn.
2. Instance scope.
3. Thread state and stack stability.
4. CPU vs IO classification.
5. Tomcat, executor, and queue saturation.
6. HikariCP active, idle, pending, and timeout metrics.
7. PostgreSQL `pg_stat_activity`, waits, locks, blocking PIDs, query age.
8. External API connect, read, write, and total deadlines.
9. Kafka consumer lag, rebalance rate, poll interval, handler latency.
10. Restart, rollback, throttle, or feature flag decision.
11. Evidence preservation.
12. Post-incident corrective actions.

The important part is not the list.

The important part is how you prioritize under pressure.

## Practice prompts

Answer these out loud.

1. A Java thread has been RUNNABLE for one hour. What do you check?
2. All Tomcat request threads are busy, CPU is low, and Hikari pending is high. What is your hypothesis?
3. A Kafka consumer group lag spikes after a partner API latency spike. What do you do first?
4. PostgreSQL shows many sessions waiting on `transactionid`. What does that imply?
5. Three thread dumps show the same threads waiting on `Future.get`. How do you proceed?
6. A restart clears the issue for five minutes and then it returns. What does that tell you?
7. How do you avoid making a retry storm worse?
8. What evidence do you capture before killing a JVM?
9. When is a rollback safer than a restart?
10. How do you explain uncertainty to executives during the incident?

## Principal interview checklist

Before the interview, make sure you can do the following:

- define RUNNABLE, BLOCKED, WAITING, and TIMED_WAITING accurately
- explain why a blocked thread may be a symptom, not root cause
- read a basic Java thread dump
- identify PostgreSQL lock waits
- explain HikariCP active vs pending connections
- describe socket timeout failures
- explain bulkheads and circuit breakers
- detect thread pool starvation
- avoid unsafe restart reflexes
- separate immediate mitigation from RCA
- produce corrective actions tied to controls

## Closing principle

Real production incidents reward disciplined curiosity.

Do not guess from one signal.

Do not worship one tool.

Do not confuse clearing symptoms with fixing the system.

In a Principal interview, your answer should make the interviewer believe the service is safer because you are on call.
