## Producer code — controller + custom key + transaction

**`PaymentController`** is the easiest interview entry point:

```java
String key = PaymentKeyStrategy.forPayment(request.accountId(), request.paymentId());
kafkaTemplate.executeInTransaction(ops -> {
    ops.send(PaymentTopics.PAYMENT_REQUESTS, key, event);
    return null;
});
```

Remember it like this:

1. REST request arrives
2. build key from business identity
3. send inside producer transaction
4. consumer gets same-account ordering

### Why this key?

```java
accountId + ":" + paymentId
```

- same account stays on the same partition
- ordering is easier to explain
- hot partition risk is visible if one account floods traffic

## Producer properties — batching, accumulator, compression

From `payment-api/src/main/resources/application.yml`:

```yaml
spring:
  kafka:
    producer:
      acks: all
      retries: 10
      transaction-id-prefix: payment-api-tx-
      properties:
        enable.idempotence: true
        compression.type: zstd
        linger.ms: 25
        batch.size: 65536
        buffer.memory: 33554432
        max.in.flight.requests.per.connection: 5
```

Easy way to explain:

- `linger.ms` + `batch.size` = producer accumulator waits a little and forms batches
- `compression.type=zstd` = fewer bytes over network
- `acks=all` + `enable.idempotence=true` = safer writes
- `max.in.flight.requests.per.connection=5` = keep throughput but stay safe with idempotence

## Consumer code — manual commit, retry, DLQ

Container config:

```java
factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
factory.setCommonErrorHandler(errorHandler(kafkaTemplate));
```

Listener:

```java
@KafkaListener(topics = PaymentTopics.PAYMENT_REQUESTS, groupId = "settlement-worker")
void onPayment(PaymentRequestedEvent event, Acknowledgment acknowledgment) {
    settlementService.process(event);
    acknowledgment.acknowledge();
}
```

Meaning:

- **no auto commit**
- offset moves only after business logic succeeds
- if processing throws, offset is not acked
- error handler decides retry or DLQ

## DLQ practical implementation

```java
DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(
        kafkaTemplate,
        (record, ex) -> new TopicPartition(PaymentTopics.PAYMENT_REQUESTS_DLT, record.partition()));
DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2L));
handler.addRetryableExceptions(TransientSettlementException.class);
handler.addNotRetryableExceptions(PoisonPaymentException.class, IllegalArgumentException.class);
```

Interview memory trick:

- **Transient** => retry
- **Poison** => DLQ now
- **Same partition** => easier replay and forensic analysis

## Serialization / deserialization

Producer:

```yaml
value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
spring.json.add.type.headers: false
```

Consumer:

```yaml
value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
spring.json.value.default.type: com.vibhu.kafka.common.PaymentMessages$PaymentRequestedEvent
spring.json.trusted.packages: com.vibhu.kafka.common
```

This gives you a concrete answer when the interviewer asks:

> “How do you stop random class deserialization issues?”

Answer:

- trusted packages
- explicit default type
- one shared event module

## Partition assignment policy

Consumer uses:

```yaml
partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

Why this is practical:

- fewer full rebalances during rolling deploys
- better partition stickiness
- easier to explain than abstract rebalance theory

## Failure matrix — producer and consumer

| Failure | Where | What this code does |
|---|---|---|
| Broker slow | producer | accumulator batches with `linger.ms`, retries 10 times |
| Duplicate send risk | producer | idempotence enabled |
| Record too big | producer/broker | broker `message.max.bytes` set; app payload still should stay small |
| Bad JSON / poison event | consumer | `PoisonPaymentException` -> DLT |
| Bank timeout | consumer | `TransientSettlementException` -> 2 retries then DLT |
| Duplicate delivery | consumer | `processed_payments` table dedupes by `payment_id` |
| Crash before ack | consumer | manual commit means record is replayed |
| Hot account | partitioning | custom key preserves order but may concentrate load |

## Broker properties

From `docker-compose.yml`:

```yaml
KAFKA_CFG_AUTO_CREATE_TOPICS_ENABLE: "false"
KAFKA_CFG_NUM_PARTITIONS: "6"
KAFKA_CFG_MESSAGE_MAX_BYTES: "2097152"
KAFKA_CFG_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: "1"
```

Easy explanation:

- do not rely on random auto-created topics
- choose partition count intentionally
- size guardrails stop giant events
- transaction log settings matter when you use producer transactions

## The 30-second interview answer

> I explain Kafka using one payment story. A Spring `payment-api` controller receives the request, derives a business key like `accountId:paymentId`, and produces JSON to `payment.requested.v1` with idempotence, compression, batching, and a producer transaction enabled. A `settlement-worker` consumes with `enable-auto-commit=false` and `MANUAL_IMMEDIATE` ack mode, so offsets move only after business logic succeeds. Transient bank errors retry through `DefaultErrorHandler`; poison messages go to a same-partition DLQ using `DeadLetterPublishingRecoverer`. I also dedupe on `payment_id`, use `CooperativeStickyAssignor` for safer rollouts, and publish result events for both success and failure. That gives me a complete producer-to-DLQ story instead of theory.
