        Cons->>Result: Publish status=SETTLED
        Cons->>Cons: Commit offset (acknowledge)

        Bank-->>Cons: timeout/5xx

## Producer properties — must set

| Property | Set | Why |
|---|---|---|
| `acks` | `all` | payment events cannot be fire-and-forget |
| `enable.idempotence` | `true` | reduce duplicate sends on retry |
| `retries` | high | transient broker/network recovery |
| `max.in.flight.requests.per.connection` | `&lt;=5` | ordering safety with idempotence |
| `delivery.timeout.ms` | finite | fail fast enough for caller SLA |
| `linger.ms` | `10-50` | batch creation in accumulator |
| `batch.size` | `32768-131072` | better throughput per request |
| `compression.type` | `zstd` or `lz4` | reduce broker and network load |
| `buffer.memory` | sized | avoid producer backpressure spikes |
| `transactional.id` | set | transactional send path |
| `value.serializer` | JSON/Avro/Proto | consistent schema strategy |
| `request.timeout.ms` | tuned | avoid hanging publish calls |

## Producer properties — description table

| Property | Description |
|---|---|
| `bootstrap.servers` | Kafka broker endpoints producer connects to. |
| `key.serializer` | Converts message key (for partition routing) to bytes. |
| `value.serializer` | Converts event payload to bytes (JSON/Avro/Proto). |
| `acks` | How many replicas must confirm write before success response. |
| `enable.idempotence` | Prevents duplicate records from producer retries. |
| `retries` | Number of resend attempts for transient send failures. |
| `max.in.flight.requests.per.connection` | Max unacked requests per broker connection; affects ordering on retry. |
| `delivery.timeout.ms` | Total allowed time for send to succeed (including retries). |
| `request.timeout.ms` | Max wait time for broker response per request. |
| `retry.backoff.ms` | Delay before retry attempt after a send failure. |
| `linger.ms` | Wait time to accumulate records before sending a batch. |
| `batch.size` | Byte target per batch in producer accumulator. |
| `buffer.memory` | Total memory for unsent records in producer buffer. |
| `compression.type` | Compression codec used for produced batches. |
| `max.request.size` | Max size of single produce request. |
| `transactional.id` | Enables transactional producer identity for EOS writes. |
| `transaction.timeout.ms` | Max time broker allows an open producer transaction. |
| `client.id` | Logical producer client name for logging/metrics. |

## Consumer properties — must set

| Property | Set | Why |
|---|---|---|
| `enable.auto.commit` | `false` | commit only after business success |
| `auto.offset.reset` | explicit (`earliest/latest`) | predictable startup behavior |
| `isolation.level` | `read_committed` | if producer is transactional |
| `max.poll.records` | bounded | avoid giant processing batches |
| `max.poll.interval.ms` | tuned to handler time | avoid rebalances mid-processing |
| `session.timeout.ms` | tuned | avoid false death detection |
| `heartbeat.interval.ms` | `< session/3` | stable group membership |
| `partition.assignment.strategy` | `CooperativeStickyAssignor` | smoother rolling deploy rebalances |
| `value.deserializer` | explicit | stable event mapping |
| `spring.json.trusted.packages` | narrow list | deserialization safety |
| `allow.auto.create.topics` | `false` | avoid typo-created topics |
| `max.partition.fetch.bytes` | sized to event | avoid fetch truncation issues |

## Broker properties — must set

| Property | Set | Why |
|---|---|---|
| `auto.create.topics.enable` | `false` | control topic lifecycle |
| `num.partitions` | intentional | concurrency and ordering balance |
| `default.replication.factor` | cluster policy | resilience |
| `min.insync.replicas` | `>=2` in prod | stronger durability with `acks=all` |
| `unclean.leader.election.enable` | `false` | avoid data loss risk |
| `message.max.bytes` | bounded | stop oversized payload incidents |
| `replica.fetch.max.bytes` | >= message max | replica sync compatibility |
| `log.retention.hours` | business + compliance | data replay window |
| `log.cleanup.policy` | `delete/compact` per topic | storage and semantic fit |
| `transaction.state.log.*` | valid values | transactional producer support |
| `offsets.topic.*` | capacity tuned | stable consumer-group operations |
| `group.initial.rebalance.delay.ms` | tuned | rebalance stability |

## Security properties — must set in prod

| Layer | Properties |
|---|---|
| Producer | `security.protocol`, `sasl.mechanism`, `sasl.jaas.config`, SSL truststore/keystore |
| Consumer | same as producer + strict truststore |
| Broker | listener security map, inter-broker protocol, authorizer, ACL strategy |

If these are missing in prod, your “working local Kafka” setup is not production-ready.

## Corner case checklist — producer side

| Symptom | Likely property issue | Fix |
|---|---|---|
| High publish latency | `linger.ms` too high + low load | reduce linger |
| Too many tiny requests | `linger.ms=0`, `batch.size` too small | increase batching |
| OOM in producer | `buffer.memory` too high for pod | lower buffer or raise memory limit |
| Duplicate sends | idempotence off | enable idempotence |
| Out-of-order on retry | `max.in.flight` too high | keep &lt;=5 with idempotence |
| Message too large error | `max.request.size` / broker max mismatch | align limits both sides |

---

## Corner case checklist — consumer side

| Symptom | Likely property issue | Fix |
|---|---|---|
| Consumer rebalances constantly | bad session/heartbeat tuning | set heartbeat and session correctly |
| Lag keeps growing | `max.poll.records` too high + slow handler | lower poll size, scale consumers |
| Duplicates after restart | auto-commit on | disable auto-commit + manual ack |
| Stuck partition | poison message retried forever | classify exception + DLQ policy |
| Deserialization crashes | trusted package/type not set | set explicit type and package |
| Read uncommitted tx data | isolation default | use `read_committed` |

---

## Corner case checklist — broker side

| Symptom | Likely property issue | Fix |
|---|---|---|
| Random topics appear | auto-create enabled | disable auto-create |
| Data loss after broker failover | unclean leader election on | turn it off |
| Replica fetch errors | replica fetch max < message max | increase replica fetch bytes |
| Transactional producer errors | tx state log config wrong | fix `transaction.state.log.*` |
| Retention not as expected | cleanup policy mismatch | set delete/compact intentionally |

## Practical GO/NO-GO before deploy

- [ ] Producer: idempotence + retry + batching + compression verified under load
- [ ] Consumer: manual commit + DLQ + retry classification tested with poison events
- [ ] Broker: topic auto-create disabled, ISR + retention policy validated
- [ ] Security: SASL/SSL + ACL tested from app pods
- [ ] Replay test: consume from earlier offset without duplicate business side effects
- [ ] Failure drill: broker restart and consumer rolling restart executed

## 30-second answer

> For production Kafka in Spring, I don’t rely on defaults. I lock producer durability (`acks=all`, idempotence, retries), throughput (`linger`, `batch`, compression), consumer correctness (manual commit, `read_committed`, controlled poll limits, cooperative assignment), and broker guardrails (no auto-topic-creation, ISR/retention/transaction-log settings). Then I validate poison handling with DLQ and replay safety before deployment.
