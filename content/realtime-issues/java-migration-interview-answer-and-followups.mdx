## How to use this page

If feedback says you have used Java 17 but look weak on upgrade risk, do **not** invent a migration you led.

Use these scripts to show lifecycle competence with clean ownership boundaries.

Anchor takeaway:

> "I understand the migration as a compatibility, dependency, regression and operational-risk exercise, with baseline testing, dependency remediation, staged rollout and rollback."

## 30-second answer

```text
I have hands-on development experience with Java 17, but I would distinguish that from having personally led a complete legacy Java 11-to-17 migration. I would treat the upgrade as a compatibility exercise: inventory Spring and third-party dependencies, baseline critical behavior, align CI and runtime images, remediate incompatible libraries, prove parity with regression and performance tests, then canary with a clear rollback—not just change the Maven Java version.
```

## 2-minute answer

```text
I have hands-on development experience with Java 17, but I would distinguish that from having personally led a complete legacy Java 11-to-17 migration. From an engineering perspective, I understand that such an upgrade is not just changing the JDK version. I would first baseline the existing application, inventory the Spring and third-party dependencies, check Java 17 compatibility, identify deprecated APIs and reflection-based libraries, and update the build and CI/CD runtime.

I would then remediate dependency conflicts and vulnerabilities, upgrade Spring components where required, and run the full unit, integration, contract, regression and performance test suites. For a financial application, I would pay particular attention to transaction processing, serialization, database behavior, Kafka integration, security and date/time functionality.

For rollout, I would use a staged or canary deployment, compare key business and technical metrics against the existing Java 11 version, and maintain a clear rollback strategy. I would also avoid combining too many major changes in one release unless there was a strong reason, because separating Java, Spring and dependency changes makes regression analysis much easier.
```

Use the 2-minute answer as your default spoken version.

It is the user-provided safe practical example, tightened for delivery.

## 5-minute answer

Expand the 2-minute answer with this skeleton:

1. **Honest ownership boundary** — used Java 17; not claiming full legacy program lead.
2. **Lifecycle** — inventory → baseline → toolchain → compatibility → remediate → test → canary.
3. **Compatibility** — Spring/Hibernate/JDBC/agents/reflection/encapsulation.
4. **Phasing** — Java and Spring related but separately controlled.
5. **Build alignment** — local/CI/Docker/runtime same major.
6. **Regression pack** — before/after payment, Kafka, DB parity.
7. **Rollout/rollback** — percentage ramp, stop conditions, expand/contract schema.
8. **Close** — migration is compatibility + operational risk, not a compiler property.

Spoken close:

```text
So if I joined a team facing this upgrade, I would not start by editing java.version.
I would start by making the risk visible and the rollback real.
```

## If they ask: "What could actually break?"

> "The major risks are usually not Java syntax changes. They're runtime and ecosystem compatibility issues—old Spring or Hibernate versions, libraries using reflection or internal JDK APIs, incompatible bytecode, JDBC drivers, serialization behavior, security libraries, build plugins, container images, and changes in performance or GC behavior. That's why I treat the migration as an application compatibility exercise and validate behavior through regression and production-like testing."

## If they ask: "Have you done this?"

Stay precise.

Good:

```text
I have shipped features on Java 17 and I understand the migration lifecycle end to end.
I have not personally led a full legacy estate from 11 to 17, so I will not claim that ownership.
Here is how I would run it, and where I have done adjacent work such as dependency upgrades or runtime image changes.
```

Bad:

```text
Yes, I migrated everything to Java 17.
```

followed by inability to describe canary stop conditions.

## Follow-up questions

### 1. Why not upgrade Java and Spring Boot in one PR?

Because RCA and rollback become ambiguous.

If production breaks, you cannot tell whether the JDK, Jakarta namespace move, Hibernate, or Jackson change caused it.

I phase unless a support matrix forces a minimum coupled jump—and even then I still isolate schema and feature changes.

### 2. What is your first artifact on day one?

An inventory and a baseline pack.

Versions, agents, images, critical flows, and known debt.

Not a compiler bump.

### 3. How do you find libraries that will fail on Java 17?

Dependency tree analysis, vendor support matrices, `jdeps`, prior org migration notes, CI jobs running tests on JDK 17 in a branch, and runtime smoke with reflective-access logging.

### 4. When are `--add-opens` flags acceptable?

As a temporary bridge with an owner and removal plan.

Not as permanent architecture.

### 5. How do you handle an internal library with no Java 17 support?

Treat it as a program dependency: find an owner, fork/replace/upgrade, or delay the service upgrade.

Do not shade and hope.

### 6. What business metrics would you watch for a payments service?

Authorization success rate, capture/settle rates, duplicate payment indicators, latency to acquirer, Kafka payment-event lag, reconciliation breaks, and customer-visible error rates.

### 7. How do date/time bugs show up after upgrades?

Timezone default assumptions, deprecated calendar APIs interacting with new libs, JSON date format changes after Jackson upgrades, and batch jobs that key off local time boundaries.

### 8. What if unit tests are green but canary fails?

Believe canary.

Expand regression fixtures from the failing traffic shape.

Check serialization, SQL, GC, and partner API behavior under real data.

### 9. How do you roll back if the schema already changed?

Only if the schema change was backward compatible.

That is why expand/contract is part of the migration design, not an afterthought.

### 10. What is the difference between using Java 17 and migrating to Java 17?

Using Java 17 means you can write modern code on a supported runtime.

Migrating means you can move a living system with dependencies, data, traffic, and rollback constraints without lying to yourself that compile green equals production safety.

### 11. How would you staff the work?

A thin platform/runtime track (JDK images, CI, build plugins) plus service teams owning dependency remediation and regression packs, with one engineer accountable for go/no-go metrics.

### 12. What documentation would you leave behind?

Support matrix, dependency exceptions, JVM flags, canary checklist, rollback steps, and a "known behavioral differences" list.

### 13. How does this relate to security upgrades?

Often the security need (CVEs, end-of-life JDK) funds the migration.

Still run it as compatibility work; urgency does not justify skipping canary.

### 14. What would make you delay the upgrade?

No rollback path, irreversible schema coupling, critical internal library unowned, or inability to baseline financial correctness.

### 15. Give the best closing sentence.

```text
I understand the migration as a compatibility, dependency, regression and operational-risk exercise, with baseline testing, dependency remediation, staged rollout and rollback.
```

## Phrases to avoid

- "It was just a compiler change."
- "We fixed all compilation errors so we were done."
- "Java 17 is backward compatible so risk is low."
- "I led the migration" (if you did not).
- "We force-updated everything to latest."

## Phrases that score

- "controlled compatibility exercise"
- "baseline before change"
- "related but separately controlled"
- "compile ≠ behave"
- "canary against business metrics"
- "backward-compatible migrations for coexistence"
- "honest about ownership, concrete about method"
