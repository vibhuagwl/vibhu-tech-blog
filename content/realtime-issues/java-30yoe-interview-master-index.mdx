## What this master index is for

This is the hub for Java Q1 through Q100 at the 25 to 30 YOE Principal and Distinguished Engineer level.

The interview is not a trivia round.

The interviewer is trying to learn whether you can hold production state in your head while the system is moving.

They want to hear how you diagnose, mitigate, communicate, and prevent recurrence without making the incident worse.

At this level, a correct API name is table stakes.

The signal is judgment.

## What interviewers evaluate at 30 YOE

Interviewers evaluate whether you establish state before action.

They listen for whether you ask:

- Is customer impact active or historical?
- Is the symptom fleet-wide, instance-local, tenant-specific, region-specific, or dependency-specific?
- Are we seeing CPU burn, blocking, queueing, GC, IO wait, or downstream saturation?
- What evidence can we capture safely before a destructive mitigation?
- What side effects can a kill, restart, scale-out, failover, or rollback create?
- Which control prevents the same failure from recurring?

A 30-YOE answer should sound like an operator and an architect at the same time.

You should be able to say what you would do in the first five minutes, what data proves or disproves each hypothesis, and what permanent design change should follow.

## What makes a 30-YOE answer different

The junior answer starts with a tool.

The senior answer starts with a likely cause.

The Principal answer starts with state.

It separates:

- symptom from cause
- mitigation from root-cause analysis
- local recovery from fleet safety
- successful restart from durable fix
- throughput improvement from correctness preservation
- a single metric spike from a correlated incident narrative

For example, if a Java service is at 100 percent CPU, the weak answer is "take a thread dump and restart."

The Principal answer is:

> I would first establish blast radius and whether the CPU is user CPU, kernel CPU, GC CPU, or a small number of hot Java threads. I would correlate `top -H`, JVM thread dumps, JFR or async-profiler, GC logs, request latency, queue depth, dependency latency, and recent config changes. If I need to restart, I would think through side effects: in-flight payments, Kafka rebalance, cache stampede, connection surge, and whether all pods will repeat the same hot path after restart.

That is the style expected throughout this curriculum.

## Core answer shape

Use this shape for most Q1 through Q100 answers:

```text
1. Establish current state and blast radius.
2. Protect customers and dependencies from cascade.
3. Capture the cheapest safe evidence.
4. Correlate dumps, metrics, traces, logs, and recent changes.
5. Pick the smallest mitigation that changes the bad state.
6. Explain side effects of kill, restart, scale, rollback, or failover.
7. Verify recovery with leading and lagging indicators.
8. Convert the incident into prevention controls.
```

The order matters.

Taking perfect dumps while the retry storm destroys the database is not good incident command.

Restarting all pods without preserving evidence may hide the leak and create the next incident.

Scaling consumers without understanding downstream saturation may convert lag into database failure.

## How to study the first 32 questions

Do not memorize the answers as scripts.

Memorize the reasoning pattern.

For each question, rehearse five sentences:

1. The state you establish.
2. The hypotheses you separate.
3. The evidence you correlate.
4. The mitigation you choose and its side effects.
5. The prevention control you would add.

If the interviewer interrupts, stay calm and keep the frame.

For example:

> Before I restart that JVM, I want one or two low-cost artifacts if the process is stable enough: thread dumps, heap or class histogram depending on symptom, GC logs, and request traces. If customers are actively failing, I may mitigate first, but I will call out the evidence loss and the side effects of restart.

That sentence sounds different from a tool list.

It shows ownership.

## Red flags in 30-YOE answers

Avoid these patterns:

- "I would just restart the pod."
- "I would increase heap."
- "Kafka guarantees exactly once, so duplicates are impossible."
- "Async will make it faster."
- "More threads will improve throughput."
- "The database is slow" without query, lock, pool, and wait evidence.
- "GC is the problem" without allocation rate, pause, heap occupancy, and CPU context.
- "We can reproduce in QA" without explaining data volume, concurrency, topology, and timing differences.

Each of these may be true in a narrow case.

At Principal level, the issue is not whether the sentence can be true.

The issue is whether you can prove it safely.

## Interviewer follow-up themes

Expect follow-ups that test whether your answer survives pressure:

- "Customers are failing now. Are you still taking dumps?"
- "What if the thread dump pauses the JVM?"
- "What if the pod is in Kubernetes and about to be killed by liveness?"
- "What if restarting triggers Kafka rebalance?"
- "What if the database is already at max connections?"
- "What if the heap dump contains customer data?"
- "What if the issue disappears after restart?"
- "What if increasing heap makes GC pauses worse?"
- "What if the downstream is rate-limiting you?"
- "What if only one tenant is affected?"

The best answers do not become defensive.

They revise the action based on state.

## Final framing

A 30-YOE Java interview is not testing whether you have seen every incident.

Nobody has.

It is testing whether you know how incidents lie.

Metrics can mislead when viewed alone.

Thread states can mislead when interpreted without CPU.

Kafka health can mislead when consumers heartbeat but handlers are blocked.

Restart can look like recovery while deleting the only evidence.

The Principal pattern is to establish state, correlate evidence, mitigate with side-effect awareness, and institutionalize the fix.

Use that pattern across Q1 through Q100.
