## Q33. How do you handle Spring Boot upgrade issues in a mature estate?

First I would establish the production shape of the Spring Boot upgrade before changing code or configuration. At Principal level, I want the invariant, the scarce resource, and the rollback path to be explicit.

- Diagnose: inventory runtime Java, Spring Boot, Spring Cloud, Hibernate, servlet stack, security filters, starters, build plugins, actuator exposure, generated SQL, and serialization contracts before touching versions.

- Evidence: compare dependency trees, startup logs, actuator `/conditions`, smoke-test traces, JFR startup recordings, canary error rates, database query fingerprints, and contract tests against the current baseline.

- Mitigate: upgrade one representative service through compile, unit, slice, integration, smoke, load, and canary stages; freeze broad rollout until behavior, not just compilation, is proven.

- Contain blast radius: route only low-risk traffic to the canary, keep the old image deployable, avoid schema changes in the same step, and pin Spring Cloud or Jakarta transitions so failures are attributable.

- Recover safely: if the canary fails, roll back the artifact and preserve evidence: dependency tree, thread dump, heap histogram if needed, JFR, request samples, and database plan differences.

- Prevent recurrence: create a platform upgrade playbook with compatibility matrices, BOM ownership, automated OpenRewrite recipes where useful, and contract tests for JSON, security, persistence, and actuator endpoints.

- Concrete tooling: keep dashboards and runbooks around the exact signals named above, plus application logs with correlation ids, distributed traces, JFR when JVM behavior is suspect, and database views such as `pg_stat_activity` or `pg_locks` when persistence is involved.

- Trade-off: aggressive upgrades reduce long-term risk but compress multiple failure modes; staged upgrades cost coordination but keep the blast radius visible.

- What not to do: do not bump the parent version across hundreds of services, merge Jakarta namespace changes with business features, or silence migration warnings with broad exclusions.
