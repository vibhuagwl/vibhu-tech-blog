## Start with a failure — not a triangle

Two payment database replicas (Bangalore and Mumbai). A customer withdraws money. The network between replicas breaks. Both nodes are still alive. Now the system must choose: **return correct data** or **return a response**.

That fork is the heart of CAP.

> Full interactive tutorial (architecture diagrams, Spring Boot CP/AP code, partition simulator, 2-minute interview answer): **[/cap-theorem/](/cap-theorem/)**

## The three properties (production language)

- **Consistency (C):** if I write ₹500, can another node still return the old ₹1000? Strong C says no.
- **Availability (A):** will a non-failed node respond (non-error)? CAP-A is not an uptime marketing SLA.
- **Partition tolerance (P):** can the system survive communication failure between nodes?

In a real multi-node system, partitions are not optional. The practical choice during a partition is usually **CP vs AP**.

## CP vs AP in one picture

```text
                 NETWORK BREAK
                      ❌
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
             CP                AP
        "Be correct"      "Stay available"
        Reject / Wait     Accept / Stale
```

## Design questions

1. What data can be stale?
2. Which operations must never double-apply (money, seats)?
3. What happens when the partition heals?
4. Do different APIs in the same product need different choices?
