## 21. Explain Kafka producer internals

```text
send(record)
  → serialize key/value
  → partitioner
  → accumulator (batches per partition)
  → sender thread
  → ProduceRequest to leader
  → wait for acks (per config)
  → retry / metadata refresh on errors
```

Key ideas: **batching**, **async I/O**, **metadata cache**, **retries**, optional **idempotence/transactions**.

## 22. `acks=0` vs `acks=1` vs `acks=all`

| acks | Meaning | Loss risk |
|---|---|---|
| `0` | Fire and forget | High |
| `1` | Leader wrote to local log | Lose if leader dies before replicate |
| `all` / `-1` | All **ISR** acknowledgments (gated by min.insync.replicas) | Lowest with proper RF/minISR |

**Payments:** `acks=all`.

## 23. What is `min.insync.replicas`?

Minimum ISR size required for `acks=all` produce to succeed.

Example: RF=3, `min.insync.replicas=2` → tolerate one broker loss without accepting under-replicated writes.

If ISR shrinks below minISR → producer gets errors (availability down, durability up).

## 24. How do you prevent message loss?

| Layer | Setting / practice |
|---|---|
| Produce durability | `acks=all`, RF≥3, `min.insync.replicas≥2` |
| Unclean election | disabled |
| Producer retries | sufficient `delivery.timeout.ms` / retries |
| Idempotence | on (for safe retries) |
| Don’t ignore callbacks | handle failures; don’t assume success |
| Disk / flush | understand `flush` vs ack semantics; rely on Kafka replication model |
| Consumer side | loss of *processing* ≠ Kafka loss — separate problem |

## 25. What is producer idempotence?

Producer gets a **PID** + sequence numbers per partition. Broker dedupes retried produce batches so **network retries don’t create duplicates in the log** for that producer session.

## 26. How does Kafka prevent duplicate messages?

Clarify layers:

| Layer | What it prevents |
|---|---|
| Idempotent producer | Duplicates from **producer retries** into the same partition log |
| Transactions + EOS | Atomic multi-partition writes + exactly-once consume-transform-produce **within Kafka** |
| Application idempotency | Duplicates from **at-least-once consume**, replays, multi-region |

Kafka alone does **not** prevent duplicate **business** payments.

## 27. What is `enable.idempotence`?

When `true`, producer uses PID/seq dedupe. Implies certain configs (`acks=all`, retries > 0, max in flight capped appropriately — modern clients set compatible defaults).

## 28. What happens when a producer retries?

On transient errors (network, NOT_LEADER, etc.) producer resends. **Without idempotence**, broker may append twice. **With idempotence**, broker rejects duplicates of same sequence.

Application must still treat consumer redelivery as normal.

## 29. Explain `delivery.timeout.ms`

Upper bound on time from `send()` until success/failure reported — includes batching + send + retries. Prefer thinking in **delivery timeout** over raw retry count for SLAs.

## 30–31. Batching, `linger.ms`, `batch.size`

| Knob | Effect |
|---|---|
| `batch.size` | Max batch bytes before send |
| `linger.ms` | Max wait to fill batch |

More batching → higher throughput, higher latency. They work together: send when size full **or** linger expires.

## 32. Tune for **low latency**

- Small `linger.ms` (0–5)
- Smaller batches
- `acks=1` only if loss OK (usually not for money)
- Enough partitions/leaders nearby
- Compression trade-off (CPU vs network)
- Avoid blocking on huge buffers; watch produce p99

## 33. Tune for **maximum throughput**

- Increase `linger.ms` and `batch.size`
- Compression (`lz4`/`zstd`)
- More partitions
- Parallelism / async sends
- Adequate buffer memory
- `acks=all` still OK if ISR healthy — durability ≠ low throughput necessarily

## 34. Producer faster than Kafka can handle?

Buffers fill → `send` blocks or throws (`max.block.ms`) → backpressure to app. If you drop on full buffer, you cause **loss**. Prefer blocking/failing loudly + scale brokers/partitions.

## 35. Producer backpressure?

1. Let buffer block (don’t silently drop).
2. Application rate limits / load shed at edge.
3. Scale partitions/brokers; fix slow ISR.
4. Quotas to protect cluster from noisy clients.
5. Async pipelines with bounded queues + metrics.

**Principal line:** backpressure is a **feature**; unbounded queues are an outage later.
