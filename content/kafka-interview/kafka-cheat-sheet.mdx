## The one story (say this in every Kafka interview)

> I explain Kafka with a payment capture flow. `payment-api` receives `POST /api/payments`, builds key `accountId:paymentId`, and publishes JSON with idempotence, batching, compression, and a producer transaction. `settlement-worker` consumes with manual offset commit, retries transient bank failures, sends poison messages to a DLQ, dedupes by `payment_id`, and publishes a result event.

If you can say that cleanly, follow-ups become easy.

## 30-second answer

> In my Spring Kafka example, the controller publishes with key `accountId:paymentId`. Producer uses `acks=all`, idempotence, compression, batching, and a transaction prefix. Consumer disables auto-commit and acks only after settlement. Transient bank errors retry; poison goes to a same-partition DLQ. A processed table prevents double settlement on replay.

---

## 90-second answer

> Client hits `payment-api`, which publishes `PaymentRequestedEvent` to `payment.requested.v1` with business key `accountId:paymentId` for per-account ordering. Producer side: idempotence, `acks=all`, `linger.ms`, `batch.size`, `compression.type=zstd` so the accumulator batches instead of spraying tiny sends.  
>
> Consumer side: `enable-auto-commit=false` and `MANUAL_IMMEDIATE`. Offsets move only after business logic. Transient bank timeout → `DefaultErrorHandler` retries. Poison → `DeadLetterPublishingRecoverer` to DLT. `processed_payments` keyed by `payment_id` blocks double charge. That is controller → broker → consumer → DLQ with real controls.

## Follow-ups (short answers)

| Question | Say this |
|---|---|
| Why this key? | Same-account ordering; watch hot partitions |
| How do offsets work? | Manual ack after success; crash → redelivery + dedupe table |
| Exactly-once? | Idempotent producer + transactional produce where needed + consumer dedupe; EOS alone does not replace DB truth |
| Lag rising? | Processing time, `max.poll.records`, partitions vs consumers, bank latency |
| Poison message? | Non-retryable exception → same-partition DLT → inspect → replay safely |
| Scale consumers? | Helps only up to partition count |

## Property flash cards

| Layer | Flash |
|---|---|
| Producer | `acks` · `linger` · `batch.size` · `zstd` · idempotence · `max.in.flight` |
| Consumer | auto-commit off · `max.poll.*` · heartbeat · CooperativeSticky · trusted packages |
| Broker | no auto-create · partitions · min ISR · message max · unclean leader off |

## Failure flash cards

| Failure | Move |
|---|---|
| Lag | poll budget + downstream |
| Rebalance storm | poll interval + sticky assignor |
| Duplicates | idempotence + processed table |
| Disk / ISR | broker capacity + unclean leader off |
| Hot key | split key strategy or isolate noisy accounts |

1. Entry — controller  
2. Producer — key, batch, compress, acks  
3. Broker — topics, partitions, limits  
4. Consumer — manual commit, assignment  
5. Failure — retry vs DLQ  
6. Safety — producer idempotence + consumer dedupe  
7. Ops — lag / poison / duplicate checks
