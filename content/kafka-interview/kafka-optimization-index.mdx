## 1. Producer optimization

| Area | Optimization |
|---|---|
| `batch.size` | Increase to improve batching and throughput |
| `linger.ms` | Small delay (2–20 ms, often 10–50 for payments) improves batching |
| `compression.type` | `lz4` / `snappy` / `zstd` — less network and disk I/O |
| `acks` | `all` for durability; `1` for lower latency |
| `enable.idempotence` | On for safe retries / duplicate protection |
| `buffer.memory` | Raise for high-throughput producers |
| `max.in.flight.requests.per.connection` | Keep ≤5 with idempotence |
| `delivery.timeout.ms` | Total time for send success including retries |
| `request.timeout.ms` | Per-request broker wait |
| `retries` | Appropriate retry budget (often high / MAX with idempotence) |
| Partitions | More partitions → more producer parallelism across leaders |
| Keying | Keys distribute load; bad keys create hot partitions |
| Async send | Prefer asynchronous `send()` + callback / Future |
| Serialization | Efficient serializers; avoid extra conversions |
| Message size | Keep records reasonably small |
| `max.request.size` | Raise only when larger records are required |

**Typical high-throughput approach:**

```text
Async + batching + linger + compression + idempotence + enough partitions
```

**Payment demo baseline (`payment-api`):**

```yaml
spring:
  kafka:
    producer:
      acks: all
      retries: 10
      properties:
        enable.idempotence: true
        compression.type: zstd
        linger.ms: 25
        batch.size: 65536
        buffer.memory: 33554432
        max.in.flight.requests.per.connection: 5
```

| Goal | Turn | Trade-off |
|---|---|---|
| Throughput ↑ | raise `linger.ms` + `batch.size`, keep compression | latency ↑ |
| Latency ↓ | lower linger, smaller batches | throughput ↓ |
| Durability | `acks=all` + idempotence | p99 ↑ slightly |
| Order under retry | `max.in.flight` ≤ 5 with idempotence | less in-flight parallelism |

**30s:** Decide throughput vs latency first. For payments keep `acks=all` + idempotence, then batch + compress. Never max every knob without measuring produce p99.

## 2. Broker optimization

The broker is where **disk, network, CPU, and memory** usually bite.

| Area | Optimization |
|---|---|
| Disk | Fast SSD / NVMe; sequential I/O wins |
| Network | Enough bandwidth for produce + fetch + replication |
| `num.network.threads` | Tune for network workload |
| `num.io.threads` | Tune for disk workload |
| `num.replica.fetchers` | Raise when replication is the bottleneck |
| Default `num.partitions` | Avoid huge defaults; create topics intentionally |
| Replication factor | Usually **3** in production |
| `min.insync.replicas` | Commonly **2** with RF=3 |
| `log.segment.bytes` | Tune segment roll size |
| `log.retention.*` | Control disk usage / replay window |
| Compression | Prefer **producer-side** compression |
| Page cache | Leave OS memory for page cache — do not give JVM everything |
| JVM heap | Modest, stable heap; Kafka loves page cache |
| GC | Predictable GC; avoid long pauses |
| Fetch / request sizes | Align `message.max.bytes` and replica fetch limits |
| Disk balancing | Spread partitions across disks and brokers |

**Common production durability set:**

```text
RF=3 + min.insync.replicas=2 + producer acks=all
```

## 3. Cluster optimization

Cluster-level work is **partition distribution, replication, capacity, and balance**.

### Partition distribution

Avoid skew:

```text
Broker 1 → 10,000 partitions
Broker 2 → 2,000 partitions
Broker 3 → 2,000 partitions
```

Prefer balanced counts **and** balanced **leaders** (not just partition count):

```text
Broker 1 → ~4,667
Broker 2 → ~4,667
Broker 3 → ~4,666
```

### Replication (important topics)

```text
replication.factor = 3
min.insync.replicas = 2
producer acks = all
```

### Capacity — monitor

```text
CPU · Memory · Disk utilization · Disk I/O · Network
Partition count · Leader count
Under-replicated partitions · ISR changes
Produce / fetch / request latency
Consumer lag
```

### Partition count

More partitions → more parallelism, but also more:

- Metadata overhead  
- Controller workload  
- File handles / memory  
- Recovery and rebalance time  
- Replication overhead  

**More partitions ≠ automatically better performance.** Size from measured parallelism ([Mastery partitions](/kafka-mastery#partitions)).

## 4. Controller optimization (KRaft)

The controller owns **cluster metadata and coordination** — not the hot path of every produce, but critical for health.

### Reduce unnecessary controller events

Avoid excessive:

- Broker restarts  
- Partition reassignment storms  
- Leader elections  
- Mass partition creation  
- Config thrash  

### Monitor

```text
Controller availability / active controller
Controller event queue depth
Metadata propagation lag
Leader election rate
Broker registration failures
Controller request latency
```

### KRaft production focus

```text
Controller quorum (odd: 3 or 5)
Metadata log durability and disk
Controller CPU / network
Metadata propagation
Quorum health
```

For larger environments, prefer **dedicated controller nodes** (`process.roles=controller`) so metadata work does not fight broker disk I/O.

## 5. Consumer optimization

Heavily driven by **partitions + consumer count + processing time**.

| Area | Optimization |
|---|---|
| Consumer count | Scale with partition count (useful members ≤ partitions) |
| `fetch.min.bytes` | Raise for throughput (fewer tiny fetches) |
| `fetch.max.wait.ms` | Allow broker to fill larger fetches |
| `max.poll.records` | Bound work per poll |
| `max.partition.fetch.bytes` | Per-partition fetch size |
| `fetch.max.bytes` | Total fetch response size |
| `enable.auto.commit` | Usually **false** for controlled processing |
| Manual commit | Commit after successful, idempotent side effects |
| Processing | Optimize downstream (bank, DB, pools) first |
| Lag | Monitor continuously (per partition + max) |
| Parallelism inside poll | Use carefully — do not blow `max.poll.interval.ms` |
| Partitions | Increase when you need more parallel consumers |

**Rule:**

```text
Max useful consumers in one group ≈ number of partitions
```

Example: 12 partitions → up to ~12 active consumers. With 20 pods, ~8 sit idle after rebalance.

**Payment demo baseline (`settlement-worker`):**

```yaml
spring:
  kafka:
    consumer:
      enable-auto-commit: false
      properties:
        max.poll.records: 50
        max.poll.interval.ms: 300000
        session.timeout.ms: 45000
        heartbeat.interval.ms: 15000
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

| Symptom | First move |
|---|---|
| Lag ↑, CPU low | Downstream slow — timeouts, pool, bulkhead |
| Lag ↑, CPU high | Smaller `max.poll.records` / faster handler |
| More pods, same lag | Partition-saturated — add partitions (planned) then pods |
| Duplicates after crash | Manual commit + idempotent sink |

## 6. Rebalance optimization

Frequent rebalances crush throughput.

Tune together:

```text
session.timeout.ms
heartbeat.interval.ms   (< session/3 typical)
max.poll.interval.ms    (> longest processing batch)
max.poll.records
```

Also:

- Static membership (`group.instance.id`) on k8s  
- Cooperative sticky assignor  
- Stable instance identity  
- Do not do unbounded work inside a single poll cycle  

Shape:

```text
poll() → process (bounded) → commit
```

so you never exceed `max.poll.interval.ms`.

## 7. End-to-end profiles

### High throughput

```text
Async producer
+ Larger batches + linger.ms
+ Compression
+ Enough partitions
+ Fast SSD + balanced brokers
+ Efficient fetch settings
+ Parallel consumers (≤ partitions)
```

### Low latency

```text
Small batches + low linger.ms
+ Light / appropriate compression
+ Fast network + disks
+ Low processing latency
+ Minimal consumer backlog
```

### High durability

```text
acks=all
+ enable.idempotence=true
+ RF=3
+ min.insync.replicas=2
+ unclean.leader.election.enable=false
```

## 8. Interview trade-offs (must say out loud)

**Throughput vs latency**

```text
larger batch + linger → higher throughput → potentially higher latency
```

**Durability vs latency**

```text
acks=all → better durability → potentially higher latency
```

**Partitions vs operational overhead**

```text
more partitions → more parallelism → more metadata / recovery / rebalance cost
```

**Compression**

```text
compression → less network + disk → more CPU
```

**Consumer parallelism**

```text
more partitions → more consumers can work in parallel → higher capacity
```

## 9. Production optimization checklist

Interview order when something is slow:

```text
1. Producer
   ├── batching / linger / compression
   ├── acks / idempotence / retries
   └── produce p99

2. Topic
   ├── partition count + key distribution
   ├── RF / minISR / retention
   └── hot partitions?

3. Broker
   ├── CPU · memory / page cache
   ├── disk I/O · network
   └── network / io / replica fetcher threads

4. Cluster
   ├── partition + leader balance
   ├── replication / ISR / URP
   └── capacity headroom

5. Controller
   ├── KRaft quorum health
   ├── metadata / elections
   └── unnecessary events?

6. Consumer
   ├── fetch / poll records
   ├── processing time + commit strategy
   └── lag + rebalance rate

7. Observability
   ├── produce / broker / fetch latency
   ├── consumer lag
   ├── under-replicated · ISR shrink
   └── disk · network utilization
```

## Corner cases

| Failure | Layer | Move |
|---|---|---|
| Chatty producer | producer | batch + linger + compression |
| Duplicate send on retry | producer | idempotence + `max.in.flight` ≤ 5 |
| Slow bank | consumer | smaller poll + retries + DLQ |
| Poison JSON | consumer | non-retryable → DLT |
| Hot account key | topic | re-key / shard whales |
| Deploy rebalance storm | consumer | CooperativeSticky + static membership |
| URP rising | broker / cluster | disk/net followers; do not enable unclean election |
| Controller thrash | controller | stop restart/reassignment storms; check KRaft quorum |

## GO before you claim “optimized”

- [ ] Named the **symptom** and the **bottleneck layer**  
- [ ] Measured produce p99 / lag / URP / disk **before** changes  
- [ ] Changed **one** layer; measured again  
- [ ] Consumer count ≤ partition count  
- [ ] Durability story intact (`acks=all`, minISR, idempotence, manual commit where needed)  
- [ ] Poison + transient paths still correct
