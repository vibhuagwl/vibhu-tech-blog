## The story

A single API server works until traffic becomes larger than one machine can safely handle. Adding a second server is easy; deciding which server should receive each request, what happens when one fails, and how connections behave during deployment is the real design problem.

## Naive architecture

```text
Client → API Server → Database
```

The server is both a capacity limit and a failure point.

## Evolving architecture

```text
Clients
   |
   v
DNS / CDN
   |
   v
Load Balancer
  /   |   \
API  API  API
  \   |   /
   Database
```

The load balancer distributes traffic across healthy instances.

## Routing strategies

- **Round robin:** simple and predictable.
- **Least connections:** useful when request duration varies.
- **Weighted routing:** useful when instances have different capacity.
- **Consistent hashing:** useful when session affinity or key locality matters.

## Health checks

A production health check should distinguish between "process is alive" and "instance can safely receive traffic." A readiness endpoint can verify critical dependencies or local state without making the load balancer depend on every downstream service.

## Failure path

If an instance fails its health checks, new traffic should stop flowing to it. Existing connections may fail and clients need timeouts and retry policies that do not create a retry storm.

## Scaling

Horizontal scaling is usually safer than continuously making one server larger. But scaling the application tier does not automatically scale the database. Always identify the next bottleneck.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| L4 balancing | Fast, simple | Less application awareness |
| L7 balancing | Content-aware routing | More processing |
| Sticky sessions | Simple session state | Uneven load / failover complexity |
| Stateless services | Easy horizontal scale | State moves to shared stores |

Discuss failure domains, deployment safety, capacity headroom, observability, cost, and who owns the load-balancing layer. Architecture is also an operational boundary.
