## Consistency: DB success, Kafka publish failed

This is the classic interview trap.

**What I say:**

> If we commit the DB and then fail to publish, downstream never sees the Cashline. I treat that as a **dual-write** risk. Preferred pattern is transactional outbox / CDC / reliable publish with retry — not “best effort after commit.”

Alternatives considered:
- Sync dual write (bad under failure)
- Outbox table + publisher
- CDC from DB change
- Orchestrator retries with idempotent publish

## Kafka unavailable

- Produce path: retry with backoff; fail request or accept with pending publish depending on product contract
- Consume path: lag grows; do not pretend processing finished
- Alert on publish error rate + lag

## Duplicate Kafka messages

Consumers must be **idempotent** using a business key / event id / unique constraint.

```text
Duplicate event
  → lookup by cashlineId + eventType/version
  → if already applied → ack and skip
  → else apply transition → persist → ack
```

## Idempotency & retries

- Retryable: timeouts, transient DB, broker blips
- Non-retryable: invalid payload, illegal status transition
- Never retry forever into poison loops — route to DLQ/error topic after budget

## Concurrency

Two updates for same Cashline: last-write-wins is usually wrong for status machines. Prefer version checks.
