## Hard production questions

### Same event twice?
Treat as at-least-once. Consumer uses event id / primary key + version / LSN / offset identity for idempotency.

### Consumer crashes mid-processing?
Offsets only advance when processing + side effects are safely completed (or outbox of effects). Restart redelivers → must be idempotent.

### DB committed but CDC delayed?
Downstream is eventually consistent. Product must tolerate lag; monitor connector lag / millisecond delay metrics.

### Missing events?
Monitor connector health, offsets, topic end offsets vs processed watermarks; reconciliation jobs for critical entities.

### Ordering?
Kafka ordering is **per partition**. Key by entity id so one entity’s changes stay ordered.

### Schema changes?
Registry compatibility (backward/forward/full). Prefer additive optional fields with defaults. Breaking changes need dual-write / dual-read plans.

## 30-second answer
> We used CDC so committed DB state became the event source. The hard part wasn’t connecting Debezium — it was idempotent consumers, ordering by entity key, and schema evolution without breaking readers.
