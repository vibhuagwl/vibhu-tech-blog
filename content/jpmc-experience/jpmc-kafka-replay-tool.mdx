> We prevent duplicate **business** processing with idempotency keys / event ids / unique constraints / state checks. Replay is at-least-once delivery; exactly-once business effect is an application property.

## Ordering

Kafka guarantees order **within a partition**. Replaying B before A across a dependency chain can break business sequencing.

Controls:
- Replay in offset order within partition
- Prefer same partition key
- Gate on state machine (reject out-of-order transitions)

## Replay frequency

Prefer **manual / controlled batches** over hot loops. Scheduled replay only with rate limits and ownership.
