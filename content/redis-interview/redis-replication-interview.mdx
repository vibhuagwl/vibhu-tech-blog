## 44–45. Primary-replica; sync or async?

Replication is **asynchronous** by default (primary doesn’t wait). `WAIT` can request sync ack from N replicas for a write — still not multi-region consensus.

## 46–50. Replica lag, backlog, partial vs full resync

- Lagging replica: continues catch-up from **replication backlog** if offset still in buffer → **partial resync (PSYNC)**.
- If backlog insufficient / ID mismatch → **full resync** (RDB transfer + catch-up) — expensive.

## 51–54. Primary fails; stale reads; replica writes; promotion

Failover (Sentinel/Cluster) promotes a replica. Reads from replicas can be **stale**. Replicas are read-only by default (`replica-read-only`). Promotion: elected replica becomes primary; others reattach.

## 55. Design for high availability

Primary + ≥2 replicas across AZs, Sentinel or Cluster, clients with failover awareness, health checks, persistence strategy, runbooks for full resync storms, app timeouts + degradation.
