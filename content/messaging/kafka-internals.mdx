# Kafka Internals: the story of one message

Imagine a payment company processing millions of events every day. The payment API should not wait for fraud checks, notifications, ledger updates, analytics and reconciliation to finish before returning.

So the architect says: **"Put the event on a durable highway and let independent teams consume it."**

That highway is Kafka.

The producer creates the event. A Kafka broker stores it inside a partition. Replicas protect it. A consumer group reads it. The application performs business work and commits progress. When something slows down, **lag becomes the smoke alarm**.

> The best Kafka mental model: **Kafka is a distributed append-only log, not simply a queue.**

![Kafka end-to-end message flow](/images/kafka/kafka-end-to-end.svg)

## 1. The 30-second mental model

```text
Producer
   |
   | serialize + key + partition
   v
Topic
   |
   +--> Partition 0 --> Leader Broker --> Followers
   +--> Partition 1 --> Leader Broker --> Followers
   +--> Partition 2 --> Leader Broker --> Followers
                                      |
                                      v
                              Consumer Group
                           +------+-----+------+
                           |             |      |
                         C1/P0        C2/P1   C3/P2
                           |             |      |
                           +-------------+------+
                                         |
                                  business processing
                                         |
                                   offset commit
```

Remember four words:

1. **Partition** = parallelism + ordering boundary.
2. **Offset** = position in a partition.
3. **Replication** = broker-side durability.
4. **Consumer group** = application-side parallelism.

## 2. Producer: how a message leaves your application

Our payment service creates:

```json
{
  "paymentId": "P1001",
  "customerId": "C42",
  "amount": 1250.00,
  "currency": "INR"
}
```

The producer does much more than `send()`.

```text
Application thread
      |
      v
Serializer
      |
      v
Partitioner <---- message key
      |
      v
RecordAccumulator
      |
      v
Batch / compression
      |
      v
Network thread
      |
      v
Partition leader broker
```

### `bootstrap.servers`

The producer needs a few broker addresses to discover the Kafka cluster. It does **not** mean every message is sent to those brokers.

### `key`

The key is usually the most important producer design decision.

```text
key = customerId
        |
        v
partition = hash(customerId) % partitionCount
```

Same key normally maps to the same partition, preserving ordering for that key while allowing other keys to run in parallel.

### Batching

Sending one network request per record is expensive. Kafka accumulates records into batches.

Important producer properties:

| Property | Why it matters |
|---|---|
| `acks` | durability/latency trade-off |
| `enable.idempotence` | protects against producer retry duplicates |
| `retries` | transient failure recovery |
| `delivery.timeout.ms` | overall send deadline |
| `request.timeout.ms` | broker request timeout |
| `linger.ms` | wait briefly to build larger batches |
| `batch.size` | target batch capacity |
| `compression.type` | network/disk efficiency |
| `buffer.memory` | producer-side memory pool |
| `max.in.flight.requests.per.connection` | ordering/retry trade-offs |
| `max.block.ms` | how long API calls may block |

### `acks`: the classic interview question

```text
acks=0   -> producer does not wait for broker acknowledgement
acks=1   -> leader acknowledges after local append
acks=all -> leader waits for required in-sync replicas
```

For important financial events, a common starting posture is `acks=all` plus idempotence, followed by load testing and explicit durability requirements.

> `acks=all` is not magic end-to-end exactly-once processing. It protects the broker-side write path; your consumer and business database still need correct semantics.

## 3. Broker: what happens when the message arrives?

The producer does not write to an abstract "Kafka topic". It sends the record to the **leader of the selected partition**.

```text
Producer
   |
   | ProduceRequest(P1)
   v
Broker 2
   |
   +--> P1 Leader
   |      |
   |      +--> append to log
   |      +--> update log end offset
   |      +--> followers fetch
   |
   +--> Broker 1 follower
   +--> Broker 3 follower
```

Kafka stores records in partition logs. Think of a partition as an ordered sequence:

```text
P1:
offset 100 -> payment.created
offset 101 -> payment.created
offset 102 -> payment.refunded
offset 103 -> payment.created
```

Kafka does not normally move records around like a traditional queue. Consumers advance through positions in the log.

### Broker responsibilities

A broker participates in:

- partition leadership
- replica storage
- replication
- produce requests
- fetch requests
- group coordination
- metadata handling
- retention and log cleanup
- network I/O
- disk I/O

### Important broker properties

| Property | Architect concern |
|---|---|
| `log.dirs` | where partition data lives |
| `num.network.threads` | network request handling |
| `num.io.threads` | request processing |
| `num.replica.fetchers` | follower replication parallelism |
| `log.retention.ms` | time-based retention |
| `log.retention.bytes` | size-based retention |
| `log.segment.bytes` | segment rolling |
| `message.max.bytes` | maximum message sizing |
| `replica.lag.time.max.ms` | ISR health signal |
| `default.replication.factor` | default topic durability |
| `min.insync.replicas` | minimum ISR for durable `acks=all` writes |

Avoid changing broker properties blindly. Kafka performance is a system problem involving CPU, memory, page cache, disk, network, partitions, request rate and workload shape.

## 4. Replication, leader and ISR

Suppose replication factor is 3.

```text
                 Partition P0
                     |
        +------------+------------+
        |            |            |
     Broker 1     Broker 2     Broker 3
      LEADER       FOLLOWER     FOLLOWER
        |            |            |
        +------------+------------+
                 replication
```

The **leader** handles normal produce/fetch traffic for that partition. Followers replicate from the leader.

The **ISR (in-sync replicas)** is the set of replicas considered sufficiently caught up to participate in the durability protocol.

![Kafka replication and ISR](/images/kafka/kafka-replication.svg)

### Why `min.insync.replicas` matters

Imagine:

```text
replication.factor = 3
min.insync.replicas = 2
acks = all
```

If only one replica remains in ISR, Kafka can reject the write rather than silently accepting a durability level below your policy.

This is a powerful interview point:

> **Replication factor tells you how many copies exist. `min.insync.replicas` tells you the minimum healthy replica set required for certain writes.**

### Leader failure

If a leader dies, Kafka can elect another eligible replica. During this period, clients may see transient errors and retry. The exact availability/durability outcome depends on ISR health and cluster configuration.

## 5. Partitions: Kafka's real unit of parallelism

A topic is a logical name. Partitions are where the real work happens.

```text
orders topic
 |
 +-- P0 -- P1 -- P2 -- P3 -- P4 -- P5
      |      |      |      |      |      |
    C1     C2     C3     C4     C5     C6
```

Within one consumer group, one partition is assigned to at most one active consumer at a time.

Therefore:

```text
partitions = 6
consumers  = 3

rough assignment:
C1 -> P0,P1
C2 -> P2,P3
C3 -> P4,P5
```

But:

```text
partitions = 3
consumers  = 10
```

Seven consumers have no partition to process.

> **You cannot get unlimited consumer parallelism without enough partitions.**

### The hot-partition trap

Suppose you key everything by:

```text
key = country
```

and India generates 80% of traffic. Hashing still sends all India records to one partition. Your cluster may look healthy while one partition melts.

Better keys usually have high cardinality and align with ordering requirements.

---

## 6. Ordering: what Kafka actually guarantees

Kafka ordering is **per partition**.

```text
P0: A1 -> A2 -> A3 -> A4   ordered
P1: B1 -> B2 -> B3 -> B4   ordered
```

Kafka does not promise:

```text
A1 -> B1 -> A2 -> B2
```

across partitions.

If payment events for one account must be ordered, use a stable account/payment aggregate key so those events land on the same partition.

Interview trap:

> Increasing partitions can change partition distribution for future records. Never assume a partition-key design is permanently safe merely because it worked at small scale.

## 7. Consumer: the other half of the story

A consumer group is an application identity.

```text
Topic: payment-events

Consumer Group: payment-ledger
   |
   +-- Consumer C1 -> P0,P1
   +-- Consumer C2 -> P2,P3
   +-- Consumer C3 -> P4,P5
```

A consumer does not receive a broker "push" of each record. It generally **fetches** records from brokers.

```text
Consumer
   |
   | FetchRequest(offset=102)
   v
Broker leader
   |
   | records 102..120
   v
Consumer poll()
   |
   v
business processing
   |
   v
offset commit
```

### Critical consumer properties

| Property | Why it matters |
|---|---|
| `group.id` | defines consumer group identity |
| `enable.auto.commit` | controls automatic offset commits |
| `auto.offset.reset` | behavior when no valid committed offset exists |
| `max.poll.records` | records returned per poll |
| `max.poll.interval.ms` | maximum interval between polls |
| `session.timeout.ms` | group membership failure detection |
| `heartbeat.interval.ms` | heartbeat cadence |
| `fetch.min.bytes` | minimum broker response payload target |
| `fetch.max.wait.ms` | broker fetch wait time |
| `max.partition.fetch.bytes` | per-partition fetch sizing |
| `fetch.max.bytes` | overall fetch response sizing |
| `partition.assignment.strategy` | how partitions are assigned |

### `max.poll.interval.ms` interview trap

If processing one batch takes too long, the consumer may stop polling within the configured interval. Kafka can conclude that the member is unhealthy and rebalance the group.

So increasing `max.poll.records` can accidentally make rebalances worse if processing time grows with batch size.

## 8. Offsets: the bookmark in the story

Think of the committed offset as a bookmark.

```text
Partition P0

100 101 102 103 104 105 106
            ^
       committed = 103
```

The consumer can fetch ahead of the committed offset. Therefore the committed offset is not necessarily "the last record currently in memory".

### The dangerous sequence

```text
1. poll records
2. process database transaction
3. crash
4. offset was not committed
5. records are fetched again
```

That is why **at-least-once processing commonly produces duplicates**.

### Correct mental model

```text
Kafka offset commit = consumer progress
Database commit     = business side effect
```

They are separate unless you deliberately build a transactional design around them.

---

## 9. Delivery semantics: at-most-once, at-least-once, exactly-once

### At-most-once

Commit/advance before processing.

```text
offset commit -> process
```

A crash can lose work.

### At-least-once

Process first, commit after successful processing.

```text
process -> commit
```

A crash between those steps can produce duplicates.

### Exactly-once

Kafka has transactional/idempotent mechanisms, but exactly-once is an **end-to-end property** only when the entire workflow participates correctly.

For example:

```text
Kafka transaction
   + Kafka output topic
   != automatically exactly-once DB update
```

A database side effect needs its own correctness mechanism, such as an idempotency key, transaction boundary, inbox/outbox pattern, or a carefully designed integration.

## 10. Consumer lag: the smoke alarm

A simple mental model is:

```text
lag ≈ latest available offset - consumer progress
```

![Kafka consumer lag diagnosis](/images/kafka/kafka-lag.svg)

Lag is not automatically an incident. A batch workload may intentionally create temporary lag. The dangerous signal is **persistent or accelerating lag**, especially when business SLA is being missed.

### Lag diagnosis: do not immediately add consumers

Ask these questions in order:

1. Is one partition hot?
2. Is producer traffic increasing?
3. Are all consumers slow or only one?
4. Is downstream DB/API latency high?
5. Is CPU or GC high?
6. Are consumers rebalancing?
7. Is the broker/network saturated?
8. Is replication falling behind?
9. Are messages unusually large?
10. Is there backpressure or throttling?

### When adding consumers helps

```text
partitions = 12
consumers  = 4
```

Adding consumers can increase parallelism.

But:

```text
partitions = 4
consumers  = 20
```

Adding more consumers does not create more partition-level parallelism.

### When adding consumers does NOT help

If one partition contains 80% of traffic, ten consumers still cannot process that single partition concurrently within the same group.

Fix the key distribution or partitioning strategy instead.

## 11. Rebalancing: why a healthy-looking consumer can still hurt throughput

A rebalance changes partition ownership inside a consumer group.

![Kafka consumer group rebalance](/images/kafka/kafka-rebalance.svg)

Typical causes:

- consumer crashes
- rolling deployments
- autoscaling
- unstable network
- heartbeat/session failures
- processing longer than `max.poll.interval.ms`
- membership changes

### How to reduce rebalance pain

- use stable consumer membership where appropriate
- use cooperative assignment strategies where supported by your client/version
- avoid huge poll batches with very long processing time
- tune heartbeat/session settings based on workload
- keep shutdown graceful
- avoid unnecessary consumer churn during deployments

Monitor **rebalance rate and rebalance duration**, not only consumer CPU.

## 12. Retry, backoff and DLQ: don't poison the partition

Suppose payment `P1001` fails because the downstream fraud service is temporarily unavailable.

A dangerous design is:

```text
consume -> fail -> immediately retry forever -> block partition
```

A safer design is:

```text
Main topic
   |
   v
consumer
   |
   +--> transient failure -> bounded retry + backoff
   |
   +--> permanent failure -> DLQ
                         |
                         v
                   replay workflow
```

DLQ is not a garbage bin. A good DLQ record keeps:

- original payload
- original topic
- partition
- offset
- event key
- timestamp
- exception type/message
- retry count
- producer/event metadata
- correlation/trace ID

### Replay safety

Never blindly replay millions of records into production.

A replay tool should support:

```text
filter -> inspect -> throttle -> replay -> audit -> verify
```

Also prevent:

```text
DLQ -> replay -> fail -> DLQ -> replay -> infinite loop
```

---

## 13. Poison messages and partition blocking

A single malformed message can repeatedly fail.

If the consumer cannot move past it, the partition can stop making progress.

Architect options include:

- bounded retries
- retry topics with increasing delays
- DLQ
- error classification: transient vs permanent
- idempotent handlers
- operational replay tools
- schema validation before business processing

The right choice depends on ordering requirements. If strict ordering is mandatory, skipping a failed event can itself violate business correctness.

## 14. Monitoring Kafka like an architect

A serious Kafka dashboard should cover four layers.

### Producer

Watch:

- request latency
- error rate
- retries
- record send rate
- batch size
- compression ratio
- buffer exhaustion
- record queue time
- request rate

### Broker

Watch:

- CPU
- disk utilization
- disk latency
- network throughput
- request latency
- request queue size
- under-replicated partitions
- offline partitions
- ISR shrink/expand
- controller/metadata health
- log flush/segment activity where relevant

### Consumer

Watch:

- consumer lag
- records consumed rate
- fetch latency
- poll latency
- rebalance count/rate
- commit latency/errors
- consumer heartbeat/session health
- processing latency
- downstream dependency latency

### Business

Kafka metrics alone are not enough.

Also measure:

```text
payment.created -> payment.settled
                 end-to-end latency
```

The business SLA is more important than a green Kafka dashboard.

## 15. Kafka lag troubleshooting playbook

When the pager says **"consumer lag is growing"**, tell this story:

```text
                 Lag rising
                     |
             Is traffic rising?
               /           \
             yes            no
             |               |
       capacity issue    Is one partition hot?
                            /        \
                          yes         no
                          |            |
                     key/skew     consumer slow?
                                      |
                           +----------+----------+
                           |                     |
                       downstream             rebalance
                       dependency             / timeout
```

### Case A: producer suddenly doubled

Options:

- increase consumer capacity
- add partitions if partition-level parallelism is insufficient
- optimize consumer processing
- use batching/compression
- apply controlled backpressure

### Case B: one partition is hot

Adding consumers may do almost nothing.

Investigate:

- key distribution
- hashing strategy
- high-volume tenant/customer
- oversized messages
- producer partition overrides

### Case C: all consumers have high DB latency

Kafka is probably not the root cause.

Fix:

- DB indexes
- connection pool
- batch writes
- transaction size
- caching
- downstream rate limits
- database capacity

### Case D: constant rebalances

Check:

- `max.poll.interval.ms`
- processing time
- `max.poll.records`
- heartbeat/session configuration
- pod restarts
- network instability
- deployment behavior

### Case E: broker is saturated

Check:

- disk I/O
- network bandwidth
- request queue
- replication traffic
- partition count/distribution
- oversized messages
- compression
- JVM/OS pressure

## 16. Producer tuning: practical starting principles

Do not copy a magic configuration from a blog.

Instead reason from the workload.

### Low latency

Prefer smaller batching delay and tune request sizes carefully.

### High throughput

Consider:

```text
compression
batch.size
linger.ms
buffer.memory
```

The goal is fewer, fuller network requests rather than millions of tiny requests.

### Ordering with retries

Idempotence should be understood alongside retry and in-flight request settings. Modern Kafka clients make safe idempotent producer configurations easier, but architects still need to understand what ordering guarantees are required and where duplicates can appear.

---

## 17. Consumer tuning: throughput vs latency

A useful relationship is:

```text
consumer throughput
≈ batch efficiency × processing parallelism × downstream capacity
```

If processing is CPU-heavy, increase application concurrency carefully.

If processing is I/O-heavy, controlled concurrency can help.

If downstream systems are already saturated, more consumer concurrency simply moves the bottleneck downstream.

Tune together:

- `max.poll.records`
- `max.poll.interval.ms`
- fetch sizes
- application worker pool
- DB batch size
- connection pool
- retry policy

## 18. Message size: the hidden distributed-systems problem

Large Kafka messages hurt:

- network bandwidth
- broker page cache
- replication
- producer memory
- consumer memory
- serialization/deserialization
- GC
- latency

A common architectural pattern is:

```text
Kafka event
  {
    objectId,
    metadata,
    URI/reference
  }
        |
        +--> object storage / database for large payload
```

Do not turn Kafka into a binary object store just because it can carry larger records.

If large messages are unavoidable, align producer, broker and consumer message/fetch limits and test the full path.

---

## 19. Schema evolution: Kafka is only half the contract

A topic is an API between producers and consumers.

Therefore ask:

- Who owns the schema?
- Are fields backward compatible?
- Can old consumers read new events?
- Can new consumers read old events?
- How are versions identified?
- How are breaking changes rolled out?

Typical strategies include:

```text
v1 -> additive field -> v1 consumers remain compatible
```

Avoid changing the meaning of an existing field while keeping the same schema name. Semantic compatibility is as important as serialization compatibility.

## 20. Transactions, idempotency and the database boundary

This is a favorite architect interview area.

Imagine:

```text
Kafka record
   |
   v
update payment DB
   |
   v
commit Kafka offset
```

What if DB commit succeeds and the process crashes before offset commit?

The record is delivered again.

Therefore:

```text
duplicate delivery
        |
        v
idempotency key
        |
        v
safe business outcome
```

For payment systems, the business operation should usually be idempotent using a stable business identifier such as `paymentId` or a dedicated idempotency key.

---

## 21. Outbox pattern: when the source DB owns truth

Suppose a service must update its database and publish an event.

Bad design:

```text
DB commit
   |
   +---- crash ----> Kafka event never published
```

Outbox pattern:

```text
Application transaction
   |
   +--> business table
   |
   +--> outbox table
             |
             v
       CDC / publisher
             |
             v
           Kafka
```

Now the database transaction makes the business change and the intent to publish atomic from the application's perspective.

Debezium/CDC can be used to stream outbox records into Kafka, but the resulting pipeline still needs idempotency and operational controls.

## 22. Kafka vs queue: interview answer

A traditional queue often emphasizes work distribution: a message is consumed and removed from the queue.

Kafka emphasizes a durable log:

```text
append -> retain -> multiple consumers read independently
```

That enables:

```text
Topic
 |
 +--> fraud group
 +--> ledger group
 +--> notification group
 +--> analytics group
```

Each group maintains its own progress.

This is why Kafka is powerful for event-driven architectures.

## 23. Multi-region architecture

For critical financial platforms, ask:

- Is Kafka stretched across regions or replicated between clusters?
- What is the RPO/RTO?
- Which region owns writes?
- How are duplicate events handled after failover?
- How is ordering preserved?
- How is consumer offset state handled?
- How is DNS/traffic switched?
- How is replay performed?

Do not casually assume synchronous cross-region replication. It can introduce latency and operational complexity.

A common architecture is separate regional clusters with controlled replication and explicit active-active or active-passive business semantics.

## 24. Retention and storage economics

Kafka storage is a business decision.

Estimate:

```text
raw storage/day
≈ events/sec × average bytes/event × 86400

cluster storage
≈ raw storage × retention window × replication factor
```

Then account for compression, segment overhead, headroom and operational safety.

Retention is not simply "keep everything forever". Ask:

- How long must events be replayable?
- Which topics require audit retention?
- Can older data move to cheaper storage?
- What is the recovery time if replay is needed?

## 25. Common Kafka failure scenarios

### Broker dies

Expected behavior: partition leaders may move and clients retry. Verify ISR health and under-replicated partitions.

### Follower falls behind

Watch ISR shrink. Investigate disk, network, broker load and replica fetch performance.

### Consumer dies

Its partitions are reassigned. Uncommitted records can be processed again.

### Consumer is alive but processing is slow

Lag rises without necessarily showing a consumer crash. Look at processing latency and downstream dependencies.

### Producer retries

Retries can expose duplicate concerns unless idempotence and downstream handling are designed correctly.

### Network partition

Clients can see timeouts and retries. A partition may be healthy locally while clients cannot reach it.

### Poison message

Bound retries and route permanent failures to an operationally controlled DLQ/retry flow.

### Disk fills

Writes can fail and broker health can deteriorate. Retention, disk sizing, replication and alert thresholds must be designed before the incident.

## 27. Interview corner cases: rapid-fire

**Q: Can Kafka guarantee global ordering?**  
No. Ordering is per partition.

**Q: Can ten consumers process one partition concurrently in one group?**  
Not as ten active partition owners. One partition has one active consumer in a group at a time.

**Q: Does adding consumers always reduce lag?**  
No. There may be too few partitions, a hot partition, downstream bottlenecks or broker saturation.

**Q: Does `acks=all` mean exactly once?**  
No. It addresses producer/broker acknowledgement durability, not the entire business workflow.

**Q: Why do duplicates happen?**  
A crash can happen after business processing but before offset commit; producer retries can also create duplicate delivery concerns depending on configuration and failure mode.

**Q: What is the difference between replication factor and ISR?**  
Replication factor is the configured number of replicas. ISR is the currently in-sync subset.

**Q: What happens when a consumer takes too long to process a batch?**  
It can exceed `max.poll.interval.ms`, be considered unhealthy and trigger a rebalance.

**Q: Why is one partition lagging while others are healthy?**  
Usually investigate key skew, a hot tenant/key, slow processing, oversized records or partition-specific broker issues.

**Q: Should a DLQ preserve the original offset?**  
Yes, preserve source metadata for auditability and safe replay.

**Q: Can a consumer read the same record twice?**  
Yes. Design for duplicates unless your complete processing model proves stronger semantics.

**Q: Why not make every topic have 1,000 partitions?**  
More partitions increase parallelism but also metadata, file/segment, recovery, rebalance and operational overhead.

**Q: What is the first metric you check when users report delayed processing?**  
End-to-end business latency, then producer rate, consumer lag, processing latency and broker health to locate the bottleneck.

## 28. The final memory trick

When you forget Kafka details in an interview, tell the story:

```text
1. PRODUCER
   creates + serializes + keys + batches

2. PARTITIONER
   chooses partition; key controls ordering distribution

3. BROKER LEADER
   appends record to partition log

4. REPLICATION
   followers copy leader; ISR protects durability

5. CONSUMER GROUP
   partitions are distributed across consumers

6. CONSUMER
   fetches records and processes business logic

7. OFFSET
   records progress after successful processing

8. FAILURE
   retry / duplicate / rebalance / DLQ depending on failure

9. LAG
   tells you producer rate is outrunning effective consumption

10. ARCHITECT
    protects correctness, capacity, observability and recovery
```

> **Kafka is easy when you remember the story: write to a partition, replicate the log, read by offset, process safely, commit progress, and observe lag.**
