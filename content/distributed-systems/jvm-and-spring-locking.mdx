## Definition: local locking

Local locking coordinates threads that share one JVM. It is the right tool for protecting local memory, caches, counters, lazy initialization, and per-process scheduling. It is the wrong sole tool for protecting account, payment, order, or inventory invariants across multiple service instances.

Mechanism: Java lock state lives in process memory. Kubernetes scaling multiplies process memory.

Timeline:

```text
deployment replicas = 2

request 1 -> pod A -> JVM A -> local lock "account-100" acquired
request 2 -> pod B -> JVM B -> local lock "account-100" acquired

Both statements are true because the locks are different objects.
```

Java example:

```java
@Service
public class AccountControllerGuard {
    public synchronized void debit(String accountId, BigDecimal amount) {
        // One thread at a time in this bean instance and JVM.
        performDebit(accountId, amount);
    }
}
```

Failure: the code passes load tests with one instance and fails after autoscaling. The lock was never designed to see the second JVM.

Monitoring:

| Signal | Scope |
|---|---|
| JVM blocked threads | One pod |
| duplicate idempotency keys | Whole service |
| PostgreSQL conflicting updates | Shared database |
| payment duplicate attempts | External provider |

Pros and cons:

| Pros | Cons |
|---|---|
| Low latency | Process-local only |
| No network dependency | Lost on restart |
| Easy to reason about for local state | Dangerous when mistaken for distributed exclusion |

When to use: local locking is excellent for in-memory performance and correctness inside one JVM. Treat it as an implementation detail, not a business invariant boundary.

Interview question: "How would you demonstrate `synchronized` is insufficient after horizontal scaling?" Draw two pods, two heaps, and two separate monitor objects for the same logical key.

## `synchronized`

Definition: `synchronized` acquires a monitor associated with an object instance or `Class` object. The JVM releases it automatically when the synchronized block exits.

Mechanism:

| Form | Monitor identity | Scope |
|---|---|---|
| `synchronized (this)` | Current object | One object in one JVM |
| `synchronized method` | Current object | One bean instance in one JVM |
| `static synchronized` | Class object | One class loader in one JVM |
| `synchronized (lockObject)` | Given object reference | Threads sharing that reference |

Timeline:

```text
T0  thread-1 enters synchronized(orderLock)
T1  thread-2 blocks on same object reference
T2  thread-1 exits
T3  thread-2 enters
T4  pod B threads were never part of this queue
```

Java example:

```java
public final class OrderAccumulator {
    private final Object lock = new Object();
    private final List<String> pendingOrderIds = new ArrayList<>();

    public void add(String orderId) {
        synchronized (lock) {
            pendingOrderIds.add(orderId);
        }
    }
}
```

Failure: using interned strings or public objects as monitors can accidentally couple unrelated code. Using request-derived lock objects without reuse can fail to protect anything.

Monitoring:

| Tool | What to inspect |
|---|---|
| Java Flight Recorder | monitor enter duration |
| thread dumps | `BLOCKED` threads and monitor owners |
| Micrometer custom timer | duration inside critical section |

Pros and cons:

| Pros | Cons |
|---|---|
| Simple syntax | No timeout or fairness controls |
| Automatic release on exit | Hard to instrument directly |
| Correct for object invariants | Cannot span JVMs |

When to use: protect small object invariants and local collections when no timeout or condition queue is needed.

Interview question: "Does `static synchronized` coordinate across pods?" No. The `Class` object exists per JVM and class loader.

## `ReentrantLock`

Definition: `ReentrantLock` is an explicit Java lock with optional fairness, timed acquisition, interruptible waits, and condition variables.

Mechanism:

```java
public class LocalAccountLock {
    private final ReentrantLock lock = new ReentrantLock(true);

    public boolean tryDebit(String accountId, BigDecimal amount) throws InterruptedException {
        if (!lock.tryLock(100, TimeUnit.MILLISECONDS)) {
            return false;
        }
        try {
            debitInMemoryProjection(accountId, amount);
            return true;
        } finally {
            lock.unlock();
        }
    }
}
```

Timeline:

```text
T0  thread A calls tryLock
T1  thread A owns lock
T2  thread B waits up to 100 ms
T3  thread B returns false if A is still inside
T4  remote pod C is unaffected
```

Java example with conditions:

```java
public class BoundedLocalQueue {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Queue<String> queue = new ArrayDeque<>();
    private final int capacity = 100;

    public void add(String id) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.size() == capacity) {
                notFull.await();
            }
            queue.add(id);
        } finally {
            lock.unlock();
        }
    }
}
```

Failure: forgetting `unlock()` in `finally` creates a permanent local outage. Enabling fairness can reduce starvation but lower throughput.

Monitoring:

| Metric | Meaning |
|---|---|
| queue length estimate | local contention |
| wait timeout count | backpressure inside pod |
| critical section timer | TTL sizing if later replaced by distributed lease |

Pros and cons:

| Pros | Cons |
|---|---|
| Timeout and interrupt support | More verbose |
| Condition variables | Manual release required |
| Optional fairness | Still JVM-local |

When to use: use `ReentrantLock` when you need try-lock, timeout, interruptibility, or multiple conditions inside one process.

Interview question: "Why might `tryLock` be better than blocking forever?" It lets a service fail fast, shed load, or return a retryable response instead of exhausting request threads.

## `ReadWriteLock`

Definition: `ReadWriteLock` allows many readers or one writer for local shared state.

Mechanism:

```java
public class LocalPricingCache {
    private final ReadWriteLock lock = new ReentrantReadWriteLock();
    private Map<String, BigDecimal> prices = Map.of();

    public BigDecimal getPrice(String sku) {
        lock.readLock().lock();
        try {
            return prices.get(sku);
        } finally {
            lock.readLock().unlock();
        }
    }

    public void replaceAll(Map<String, BigDecimal> next) {
        lock.writeLock().lock();
        try {
            prices = Map.copyOf(next);
        } finally {
            lock.writeLock().unlock();
        }
    }
}
```

Timeline:

```text
reader A enters
reader B enters
writer C waits
reader A exits
reader B exits
writer C enters
```

Failure: under a constant read stream, writer behavior depends on implementation and fairness settings. Also, a local read lock does not make the cached value globally current.

Monitoring:

| Signal | Interpretation |
|---|---|
| read latency during refresh | writer blocking readers |
| refresh duration | write lock hold time |
| stale cache age | distributed freshness issue |

Pros and cons:

| Pros | Cons |
|---|---|
| Higher local read concurrency | More complex than immutable swap |
| Good for read-mostly state | Writer starvation risk |
| Clear read/write intent | Process-local freshness only |

When to use: read-mostly local data structures where immutable replacement is not enough or where writes must coordinate with reads.

Interview question: "Would `ReadWriteLock` protect a Redis-backed cache from stampede across pods?" No. It can reduce stampede per pod only.

## `StampedLock`

Definition: `StampedLock` supports write locks, read locks, and optimistic reads with validation. It is non-reentrant and more specialized than `ReadWriteLock`.

Mechanism:

```java
public class LocalInventorySnapshot {
    private final StampedLock lock = new StampedLock();
    private long version;
    private int available;

    public int readAvailable() {
        long stamp = lock.tryOptimisticRead();
        int value = available;
        if (!lock.validate(stamp)) {
            stamp = lock.readLock();
            try {
                value = available;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return value;
    }

    public void update(int nextAvailable) {
        long stamp = lock.writeLock();
        try {
            available = nextAvailable;
            version++;
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}
```

Timeline:

```text
T0  reader gets optimistic stamp 10
T1  writer updates value and advances stamp
T2  reader validates stamp 10
T3  validation fails
T4  reader falls back to read lock
```

Failure: using an optimistic read value without validation is a data race. Blocking while holding a stamped write lock can freeze all local readers.

Monitoring:

| Metric | Why |
|---|---|
| optimistic validation failure rate | write pressure |
| write lock duration | local read impact |
| fallback read count | whether complexity is paying off |

Pros and cons:

| Pros | Cons |
|---|---|
| Very fast read-heavy local paths | Non-reentrant |
| Optimistic read option | Easy to misuse |
| Useful for local snapshots | No distributed visibility |

When to use: highly contended local read-mostly state with careful tests and no need for reentrancy.

Interview question: "Can `StampedLock` solve duplicate payment capture?" No. It protects local memory, not external side effects.

## Spring `ConcurrentHashMap` lock manager

Definition: a common Spring pattern maps business keys to local lock objects. It gives per-key exclusion inside one application instance.

Mechanism:

```java
@Component
public class LocalKeyedLockManager {
    private final ConcurrentHashMap<String, ReentrantLock> locks = new ConcurrentHashMap<>();

    public void withLock(String key, Runnable work) {
        ReentrantLock lock = locks.computeIfAbsent(key, ignored -> new ReentrantLock());
        lock.lock();
        try {
            work.run();
        } finally {
            lock.unlock();
        }
    }
}
```

Timeline:

```text
Instance A map:
  account-100 -> ReentrantLock@A1

Instance B map:
  account-100 -> ReentrantLock@B1

A1 and B1 are unrelated.
```

Java example for the duplicate:

```java
@RestController
public class AccountController {
    private final LocalKeyedLockManager localLocks;

    @PostMapping("/accounts/{id}/debit")
    public void debit(@PathVariable String id, @RequestBody DebitRequest request) {
        localLocks.withLock("account-" + id, () -> service.debit(id, request.amount()));
    }
}
```

Failure: two Kubernetes pods both call `computeIfAbsent("account-100", ...)` and both succeed locally. If the map never removes keys, every new account or order id leaves a lock object behind.

Monitoring:

| Metric | Reason |
|---|---|
| lock map size | dynamic-key memory leak |
| keys created per minute | cardinality pressure |
| per-key wait time | hot keys inside one pod |
| heap after traffic spike | stale lock retention |

Pros and cons:

| Pros | Cons |
|---|---|
| Per-key local concurrency | Memory leak risk |
| Simple Spring bean | False sense of distributed safety |
| Useful for local request coalescing | Needs cleanup protocol |

When to use: request coalescing, local cache rebuild protection, and per-pod throttling. Avoid for durable business invariants unless paired with database enforcement.

Interview question: "Why do Instance A and Instance B both get `account-100`?" Because each has a separate `ConcurrentHashMap` in its own heap.

## Avoiding dynamic-key memory leaks

Definition: a dynamic-key leak happens when every distinct request key creates a lock object that is never removed.

Mechanism:

```java
public void withLock(String key, Runnable work) {
    ReentrantLock lock = locks.computeIfAbsent(key, ignored -> new ReentrantLock());
    lock.lock();
    try {
        work.run();
    } finally {
        lock.unlock();
        locks.computeIfPresent(key, (ignored, existing) ->
            existing.hasQueuedThreads() ? existing : null
        );
    }
}
```

Timeline:

```text
T0  traffic touches order-1 through order-1,000,000
T1  map creates 1,000,000 ReentrantLock objects
T2  orders complete
T3  map still references all locks unless cleaned
T4  heap grows until GC pressure or OOM
```

Failure: the cleanup example is subtle. Removing a lock while another thread is about to use it can split a key into two locks. Production implementations need reference counts, striping, bounded caches, or simpler designs.

Monitoring:

| Signal | Action |
|---|---|
| map size grows with unique keys | add bound or cleanup |
| old generation heap growth | inspect retained lock keys |
| lock object allocation spike | reduce cardinality |

Pros and cons:

| Approach | Pros | Cons |
|---|---|---|
| Remove when idle | Lower memory | Race-prone if implemented casually |
| Reference counted lock wrapper | Safer cleanup | More code |
| Caffeine bounded cache | Mature eviction | Dependency and eviction semantics |
| Striping | Bounded memory | Unrelated keys can block each other |

When to use: bounded or cleaned keyed locks are acceptable for local performance. If correctness matters, push enforcement to PostgreSQL, Redis with fencing, or a coordinator.

Interview question: "What is the bug in a naive `ConcurrentHashMap` lock registry?" It either leaks per-key locks forever or removes locks unsafely and breaks mutual exclusion.

## Striped locking

Definition: striped locking maps many keys onto a fixed number of local locks. It bounds memory at the cost of false contention.

Mechanism:

```java
public class StripedLocalLocks {
    private final ReentrantLock[] stripes;

    public StripedLocalLocks(int stripeCount) {
        this.stripes = IntStream.range(0, stripeCount)
            .mapToObj(i -> new ReentrantLock())
            .toArray(ReentrantLock[]::new);
    }

    public void withStripe(String key, Runnable work) {
        ReentrantLock lock = stripes[Math.floorMod(key.hashCode(), stripes.length)];
        lock.lock();
        try {
            work.run();
        } finally {
            lock.unlock();
        }
    }
}
```

Timeline:

```text
account-100 -> stripe 7
account-240 -> stripe 7
order-55    -> stripe 3

account-100 and account-240 block each other locally even though resources differ.
```

Failure: a hot key can monopolize one stripe and slow unrelated keys mapped to the same stripe. Across pods, each pod still has its own stripe array.

Monitoring:

| Metric | Interpretation |
|---|---|
| wait time by stripe | skew and hot stripes |
| operations by stripe | hash distribution |
| stripe hold duration | critical-section health |

Pros and cons:

| Pros | Cons |
|---|---|
| Bounded memory | False contention |
| Simple cleanup story | Needs good stripe count |
| Useful for local cache stampede reduction | Not distributed |

When to use: local throttling and cache rebuild coalescing where occasional unrelated blocking is acceptable.

Interview question: "How many stripes should you use?" Enough to reduce local false contention under measured load, but not so many that observability and memory become noisy.

## Kubernetes pod scope

Definition: a pod is an operational boundary, not a mutual-exclusion boundary. Each pod has its own JVM, heap, thread pools, Spring beans, and local locks.

Mechanism:

| Kubernetes event | Effect on local locks |
|---|---|
| scale out | creates more independent lock domains |
| rolling deploy | old and new pods hold separate locks |
| pod restart | all local lock state disappears |
| HPA burst | increases duplicate execution opportunities |

Timeline:

```text
T0  one pod: local lock appears safe
T1  HPA scales to five pods
T2  retry for same order lands on pod 4
T3  pod 4 local lock is free
T4  duplicate critical section runs
```

Java example:

```java
@Component
public class PodIdentity {
    @Value("${HOSTNAME:unknown-pod}")
    private String podName;

    public String localOwnerId() {
        return podName + ":" + ManagementFactory.getRuntimeMXBean().getName();
    }
}
```

Failure: logs show "lock acquired" once per pod, which can mislead responders. Include pod name, owner id, request id, and business key in every local-lock log.

Monitoring:

| Dashboard | Must group by |
|---|---|
| lock acquisitions | pod, key prefix, route |
| duplicate requests | idempotency key, customer, order |
| local contention | pod and stripe |
| invariant violations | global resource id |

Pros and cons:

| Pros | Cons |
|---|---|
| Pod-local locks are predictable | Horizontal scale weakens business protection |
| Great for local pressure relief | Rolling deploy creates overlapping domains |
| No dependency on Redis or DB | Cannot recover state after restart |

When to use: use pod-local locks deliberately for pod-local state. For account, order, payment, and inventory correctness, pair local performance tricks with PostgreSQL constraints, idempotency, Redis leases with fencing, or queue partitioning.

Interview question: "A service had no duplicates until HPA scaled it. What changed?" The concurrency domain grew from one JVM to many JVMs, but the lock authority stayed inside one JVM.
