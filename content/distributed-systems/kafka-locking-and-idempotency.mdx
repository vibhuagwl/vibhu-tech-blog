## Interview framing

Kafka often removes the need for some locks.
It does not remove the need for idempotency.

If all events for `payment_id = P1` go to the same partition, Kafka gives ordered delivery for that key inside a consumer group.
That can eliminate JVM-level locking for per-payment state machines.
It cannot prevent duplicate messages, consumer retries, external provider retries, or database races outside the partition owner.

## 20. Partition by key eliminates some locks

Kafka ordering is per partition.
The producer chooses a record key.
Kafka hashes that key to a partition.
Within one consumer group, at most one consumer instance owns a partition at a time.

```text
key payment-101 -> partition 3 -> consumer A
key payment-202 -> partition 7 -> consumer B
key payment-101 -> partition 3 -> consumer A
```

If every state transition for payment 101 uses key `payment-101`, consumer A sees those transitions in order.
You usually do not need a Java lock such as `synchronized` or `ReentrantLock` around payment 101 in that consumer process.

This only works if:

- All producers use the same keying rule.
- The topic has not been repartitioned in a way that changes ordering expectations.
- Every service that mutates the same state consumes through the same serialized path or uses database constraints.
- Rebalances are handled with idempotent processing.

Bad producer:

```java
kafkaTemplate.send("payment-events", randomUUID().toString(), event);
```

Good producer:

```java
kafkaTemplate.send("payment-events", event.paymentId().toString(), event);
```

The partition key is part of the consistency model.
Treat it like a schema field.

## Consumer groups and ownership

A topic partition is assigned to one member of a consumer group.
Different consumer groups each receive their own copy of the stream.

```text
Topic: payment-events
Group ledger-service: partition 0 owned by ledger-1
Group fraud-service: partition 0 owned by fraud-2
```

This means per-key serialization is scoped to a group.
The ledger service and fraud service can process the same payment concurrently.
If they both write the same PostgreSQL row, Kafka does not protect that row.

Use PostgreSQL ownership boundaries:

- Ledger service owns ledger tables.
- Fraud service owns fraud review tables.
- Payment service owns payment state.

If two consumers must update one row, you still need row locks, version checks, or a single owning service.

## Duplicates are normal

Kafka consumers should assume at-least-once processing.
A message can be processed, the database transaction can commit, and the process can crash before offset commit.
After restart, Kafka delivers the same message again.

Timeline:

```text
Consumer reads PaymentCaptured event at offset 91
Consumer inserts ledger row
Consumer commits PostgreSQL transaction
Process crashes before committing Kafka offset
Consumer restarts
Kafka redelivers offset 91
```

If the handler inserts blindly, you get duplicate ledger entries.
The fix is idempotency at the write boundary.

## Idempotency key plus unique constraint

An idempotency key is a stable identifier for the logical operation.
It is not a request timestamp.
It is not a random value generated on each retry.

For Kafka consumers, a good key may be:

- Event ID generated by the producer.
- Business operation ID such as capture attempt ID.
- Provider idempotency key.
- Topic, partition, and offset for strictly internal effects.

Database schema:

```sql
CREATE TABLE processed_message (
  consumer_name text NOT NULL,
  message_id text NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer_name, message_id)
);

CREATE TABLE ledger_entry (
  id uuid PRIMARY KEY,
  payment_id uuid NOT NULL,
  amount_cents bigint NOT NULL,
  entry_type text NOT NULL,
  idempotency_key text NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

Handler shape:

```java
@Transactional
public void handlePaymentCaptured(PaymentCaptured event) {
    if (!processedMessages.tryInsert("ledger-service", event.eventId())) {
        return;
    }

    ledger.insertCredit(
        event.paymentId(),
        event.amountCents(),
        event.captureAttemptId()
    );
}
```

`tryInsert` relies on the primary key.
If the row already exists, the message was processed before.

Do not store processed message IDs in an in-memory set.
A redeploy, rebalance, or new instance will forget them.

## Unique constraint as a concurrency primitive

PostgreSQL can serialize logical operations without an explicit lock.

```sql
INSERT INTO ledger_entry(
  id,
  payment_id,
  amount_cents,
  entry_type,
  idempotency_key
)
VALUES (
  gen_random_uuid(),
  $1,
  $2,
  'CAPTURE',
  $3
)
ON CONFLICT (idempotency_key) DO NOTHING;
```

The unique constraint is the lock.
It is durable, observable, and local to the invariant.

This is often better than:

```text
Acquire Redis lock
Check if ledger row exists
Insert ledger row
Release Redis lock
```

The Redis version still needs a unique constraint for correctness.
Once you add the constraint, the lock is often just latency and failure surface.

## 44. Exactly-once versus effectively-once

Kafka transactions and idempotent producers can provide exactly-once semantics for Kafka-to-Kafka pipelines when configured correctly.
They do not magically make your payment provider, email service, or PostgreSQL side effect exactly once.

Important distinctions:

| Scope | What can be exactly once | What still needs idempotency |
|---|---|---|
| Producer to Kafka | Duplicate producer sends can be fenced | Business operation IDs |
| Kafka consume and produce | Read-process-write to Kafka topics | External systems outside Kafka transaction |
| Kafka plus PostgreSQL | Not atomic by default | Database idempotency and outbox |
| Payment API | Provider may retry or time out | Provider idempotency key and reconciliation |

Effectively-once means the system may execute a handler more than once, but the durable business result is as if it happened once.

For interviews, say:

```text
Kafka gives ordered, durable delivery.
PostgreSQL gives constraints and transactions.
The application supplies stable operation IDs.
Together they produce effectively-once business outcomes.
```

## 45. Never hold a DB lock during external payment API calls

This is one of the most important production rules.

Bad flow:

```java
@Transactional
public void capture(UUID paymentId) {
    Payment payment = payments.lockForUpdate(paymentId).orElseThrow();
    if (!payment.canCapture()) {
        return;
    }

    ProviderResponse response = paymentGateway.capture(
        payment.providerIntentId(),
        payment.captureIdempotencyKey()
    );

    payment.markCaptured(response.providerReference());
}
```

The row lock is held while the service waits on the payment provider.
If the provider hangs for ten seconds, every retry and every related workflow waits behind the same database lock.
Connection pool threads pile up.
Kafka partitions stop making progress.
Deadlock diagnostics show PostgreSQL waits, but the true owner is an HTTP call.

Better flow:

```text
Transaction 1:
  lock payment row
  validate state
  create capture_attempt with unique idempotency key
  mark payment CAPTURE_PENDING
  insert outbox event
  commit

Worker:
  call payment provider with capture_attempt idempotency key

Transaction 2:
  lock payment row
  record provider result
  transition to CAPTURED or CAPTURE_FAILED
  commit
```

This design makes the database lock protect only local state.
The external provider call is retried with a stable idempotency key.

## 46. Outbox redesign

The transactional outbox turns "update database and publish event" into one local transaction.

Schema:

```sql
CREATE TABLE outbox_event (
  id uuid PRIMARY KEY,
  aggregate_type text NOT NULL,
  aggregate_id uuid NOT NULL,
  event_type text NOT NULL,
  payload jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz,
  publish_attempts integer NOT NULL DEFAULT 0
);

CREATE INDEX outbox_unpublished_idx
ON outbox_event(created_at)
WHERE published_at IS NULL;
```

Payment state transaction:

```java
@Transactional
public UUID requestCapture(UUID paymentId, String requestId) {
    Payment payment = payments.lockForUpdate(paymentId).orElseThrow();
    CaptureAttempt attempt = attempts.create(paymentId, requestId);
    payment.markCapturePending(attempt.id());
    outbox.insert("PaymentCaptureRequested", paymentId, attempt.id());
    return attempt.id();
}
```

Relay claim query:

```sql
WITH next_events AS (
  SELECT id
  FROM outbox_event
  WHERE published_at IS NULL
  ORDER BY created_at
  LIMIT 100
  FOR UPDATE SKIP LOCKED
)
UPDATE outbox_event o
SET publish_attempts = publish_attempts + 1
FROM next_events
WHERE o.id = next_events.id
RETURNING o.id, o.event_type, o.payload;
```

The relay publishes to Kafka with key `aggregate_id`.
After successful send acknowledgement, it marks `published_at`.
If it crashes between publish and mark, Kafka may receive a duplicate.
Consumers must still be idempotent.

## Rebalance handling

Consumer rebalances interrupt ownership.
A consumer may be processing records when partitions are revoked.

Production rules:

- Keep handler transactions short.
- Commit offsets only after durable side effects.
- On partition revoke, stop taking new work for that partition.
- Let in-flight work finish within a bounded shutdown budget.
- Make every handler safe to rerun.

Spring Kafka gives hooks such as consumer rebalance listeners.
Use them to pause and drain, not to perform long database repair.

## Ordering and database transactions

Kafka ordering does not automatically equal database serializability.
Suppose payment events are ordered, but an admin API can update the same payment row directly.

```text
Kafka consumer: PaymentAuthorized event
Admin API: manually cancel payment
Kafka consumer: PaymentCaptured event
```

The database remains the source of truth.
Each state transition should be conditional:

```sql
UPDATE payment
SET state = 'CAPTURED'
WHERE id = $1
  AND state = 'CAPTURE_PENDING';
```

If zero rows are updated, the event is stale or invalid for the current state.
Record it, alert if needed, and move on idempotently.

## Interview answer shape

A strong answer says Kafka reduces locking by assigning all records for a key to one partition in one consumer group.
Then it immediately adds the caveat: duplicates, rebalances, external APIs, and database side effects still require idempotency.

The Staff-level design uses Kafka for ordering, PostgreSQL for durable invariants, unique constraints for idempotency, and an outbox so local state changes and publish intent commit together.
