## The Principal decision

Every design must answer:

| Question | Principal-level answer |
|---|---|
| Who owns the lock? | A specific process attempt owns a **lease** for a key + token |
| Where is ownership stored? | Redis key, DB row, ZK node, or etcd key with lease |
| Who expires ownership? | Lock service lease, session timeout, or transaction end |
| Who fences writes? | The **resource of record** via monotonic token/version |
| Who observes failure? | Metrics, traces, audits, fence rejects |

```text
T0  A acquires token 41
T1  A pauses (GC)
T2  lease expires; B gets token 42
T3  B writes with token 42
T4  A resumes with token 41
T5  DB rejects token 41 (last_token = 42)
```

## Decision matrix

| Need | Prefer | Why |
|---|---|---|
| Duplicate payment capture | Idempotency key + unique constraint | Deduplicate at side-effect source |
| Account balance race | Postgres row lock / optimistic version | Invariant lives in DB |
| Scheduler leader | ZK / etcd lease | Membership problem |
| Short cache rebuild | Redis lock + token-safe release | Bounded, discardable work |
| Hot inventory | Atomic `UPDATE … WHERE qty > 0` or SKU queue | Stock is the resource |

```text
can a DB constraint express the invariant?  → use DB
can partition ownership serialize the key? → Kafka/queue
is work short and best-effort?             → Redis lease (+ fence if writes matter)
is leadership/membership the core?         → ZK/etcd
otherwise                                  → redesign before adding a lock
```

## Interview answer template

```text
1. Name the invariant.
2. Prefer local enforcement at the resource.
3. If a cross-process lock remains, use a lease + owner token.
4. Fence writes with monotonic tokens/versions.
5. Make retries idempotent.
6. Monitor wait, hold, expiry, renewal, fence rejects.
7. State the failure mode you intentionally accept.
```
