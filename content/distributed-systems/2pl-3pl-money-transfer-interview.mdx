## Mental model

```text
Request → idempotency claim → Redis exclusive leases (sorted)
       → PostgreSQL FOR UPDATE → debit/credit → COMMIT
       → safe unlock → COMPLETED
```

| | |
|---|---|
| **WHAT** | Serialize concurrent transfers so the ledger stays correct |
| **HOW** | Strict 2PL on Redis + row locks in Postgres + fencing + idempotency |
| **WHY** | Multiple app instances; retries; lease expiry; crash mid-flight |

### Invariants to defend

| Invariant | Why interviewers care |
|---|---|
| Balance never negative | Core money correctness |
| At-most-once debit per idempotency key | Mobile / gateway retries are normal |
| Locks held until commit or rollback | Strict 2PL — no early release |
| Stale lock holder cannot write | Fencing after lease expiry |
| Kafka off the sync path | Events must not delay locking |

## Why called 2PL and 3PL?

These names describe **two different layers**. Do not mix them in the interview.

### 2-phase locking (2PL) — how locks are held

Named for **two phases of lock lifetime**, not “two locks”:

| Phase | What happens | In this design |
|---|---|---|
| **1. Growing** | Only acquire locks — never release | Redis exclusive leases on accounts (sorted ids) |
| **2. Shrinking** | Only release locks — never acquire | After COMMIT or ABORT — safe unlock |

```text
Growing  ──►  [hold all locks while money moves]  ──►  Shrinking
 acquire                   mutate / commit                    release
```

**Strict 2PL** = no early unlock before the DB commit/rollback finishes. That is why the class is `TwoPhaseLockingManager`: `acquireLocks` then later `releaseLocks` — nothing in between returns a lock.

**Say this:** “Two-phase locking means grow then shrink. I never unlock mid-transfer, so another tx cannot see a half-updated ledger.”

### 3-phase locking / 3PL transfer protocol — how the tx progresses

Here “3-phase” means the **persisted transfer state machine** used for crash recovery (inspired by 3PC-style prepare → ready → commit), not a third lock mode:

| Phase | State(s) | Job |
|---|---|---|
| **1. Lock / prepare** | `ACTIVE` → `LOCKING` → `PRE_COMMIT` | Claim idempotency, acquire Redis leases, validate balances |
| **2. Pre-commit (ready)** | `COMMIT_READY` | Durable “I am ready to apply” — recovery can finish or abort |
| **3. Commit + release** | `COMMITTED` → `RELEASED` | Apply ledger write, then unlock (2PL shrinking phase) |

```text
Phase 1              Phase 2                 Phase 3
LOCKING/PRE_COMMIT → COMMIT_READY → COMMITTED → RELEASED
```

Mapped to code in [source](#source):

| Name | Class |
|---|---|
| 2PL | `TwoPhaseLockingManager` |
| 3PL orchestration | `ThreePhaseTransactionManager` |
| HTTP entry | `TransferService.transfer` → begin → acquireLocks → prepare → preCommit → commit → releaseLocks |

**Say this:** “2PL is the lock discipline. 3PL is the durable transfer steps so a crashed pod can recover from `COMMIT_READY` without double-debit.”

### 2PL vs 2PC vs 3PL (do not confuse)

| Acronym | About | This money-transfer page |
|---|---|---|
| **2PL** | Lock acquire/release phases | Yes — Redis leases |
| **2PC** | Distributed commit (prepare/commit across participants) | Related idea at ledger apply; not classic XA |
| **3PL / 3PC-style states** | Extra ready/recovery step | Yes — `PRE_COMMIT` / `COMMIT_READY` |

## Spoken answer (30 seconds)

> I serialize account writes with a **Redis exclusive lease** (strict 2PL: hold until commit or rollback), attach a **fencing token** so a stale holder cannot write after lease expiry, and make **PostgreSQL `SELECT … FOR UPDATE`** the final balance guardian. An **idempotency key** stops double debit on retry. **Kafka is lifecycle only** — never inside acquire→commit. If the app crashes mid-flight, recovery continues or aborts from **persisted 3PL state**.

Practice once out loud before the interview.

## Multi-microservice example (how 2PL + 3PL span services)

One process cannot hold JDBC locks across services. With **several microservices**, you still keep the same rules — but the **coordinator** is the Transaction Service, and locks live in a **shared Lock Service (Redis)**.

### Example topology (this lab)

| Microservice | Port | Owns | Role in 2PL / 3PL |
|---|---:|---|---|
| **API Gateway** | 8080 | Edge routing | Forwards `POST /transfers` |
| **Transaction Service** | 8083 | Transfer DB + 3PL state | Coordinator — grow/shrink locks, drive phases |
| **Lock Service** | 8081 | Redis leases | Exclusive lock API + fencing tokens |
| **Account Service** | 8082 | Ledger DB | `FOR UPDATE` debit/credit with fencing check |
| **Recovery Service** | 8084 | Polls stale txs | Resumes or aborts from persisted 3PL state |

```text
Client
  → Gateway
      → Transaction Service   ← 3PL state machine lives here
            → Lock Service → Redis     ← 2PL leases (cross-service)
            → Account Service → Postgres ledger
      ← Recovery Service (async) reads Transaction DB + finishes incomplete txs
```

**Interview line:** “2PL is enforced by a central lock microservice; 3PL state is stored by the transfer coordinator; each ledger service only mutates under a fencing token.”

### How 2PL works across microservices

| 2PL phase | Who does what |
|---|---|
| **Growing** | Transaction Service calls Lock Service `acquire(account:A)` then `acquire(account:B)` (sorted). No unlock yet. |
| **Critical section** | Still holding leases, Transaction Service calls Account Service prepare/apply. Other transfer pods block on Lock Service. |
| **Shrinking** | Only after COMMIT or ABORT — Transaction Service calls Lock Service `release` for A and B. |

Locks are **not** local synchronized blocks. Every Transfer pod asks the same Lock Service, so mutual exclusion works across instances and services.

### How 3PL works across microservices

| 3PL phase | Transaction Service state | Calls |
|---|---|---|
| **1. Lock / prepare** | `LOCKING` → `PRE_COMMIT` | Lock Service acquire → Account Service prepare (balance check) |
| **2. Ready** | `COMMIT_READY` | Persist “ready” in Transaction DB (crash checkpoint) |
| **3. Commit + release** | `COMMITTED` → `RELEASED` | Account Service apply → Lock Service release |

If Transaction Service dies after `COMMIT_READY`, **Recovery Service** loads that row and either finishes apply + release, or aborts + release — using fencing so a zombie pod cannot write.

### What each service must remember

| Service | Must | Must not |
|---|---|---|
| Transaction Service | Own 3PL state + call order | Unlock before commit/abort |
| Lock Service | Atomic acquire/release + fence | Care about balances |
| Account Service | Enforce balance + check fence | Trust callers without fence |
| Recovery Service | Resume from durable state | Start new business transfers |

**Say this:** “With many microservices, 2PL is a shared lock service used by every transfer instance; 3PL is the coordinator’s durable checklist so recovery can complete the money move after a crash.”

## 5. Deadlock

Always lock account ids in **sorted order** to reduce cycles. If a wait-for cycle still appears, abort one waiter.

## Basic implementation (interview-sized)

Four snippets. Enough for the whiteboard — not a multi-module repo dump.

### Redis exclusive lock + safe unlock

```java
// Acquire
Boolean ok = redis.setIfAbsent(
    "lock:" + accountId, token, Duration.ofSeconds(30));

// Unlock — only the owner may delete
String lua = """
  if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
  else
    return 0
  end
  """;
```

### PostgreSQL final guardian

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select a from Account a where a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") String id);

@Transactional
public void apply(String src, String dst, BigDecimal amount) {
  // Lock in sorted id order to reduce deadlocks
  Account first  = repo.findByIdForUpdate(min(src, dst)).orElseThrow();
  Account second = repo.findByIdForUpdate(max(src, dst)).orElseThrow();
  Account source = src.equals(first.getId()) ? first : second;
  Account dest   = source == first ? second : first;

  if (source.getBalance().compareTo(amount) < 0) {
    throw new InsufficientFunds();
  }
  source.debit(amount);
  dest.credit(amount);
}
```

### Transfer flow (strict 2PL)

```java
public TransferResult transfer(TransferRequest req) {
  if (idempotency.exists(req.key())) {
    return idempotency.get(req.key());
  }

  String[] keys = sorted(req.from(), req.to());
  LockToken t1 = locks.acquire(keys[0]);
  LockToken t2 = locks.acquire(keys[1]);
  try {
    accounts.apply(req.from(), req.to(), req.amount());
    idempotency.save(req.key(), COMPLETED);
    return COMPLETED;
  } finally {
    locks.release(t2);
    locks.release(t1);
  }
}
```

### Why both Redis and Postgres?

| Layer | Job in the design |
|---|---|
| Redis exclusive lease | Cross-instance mutual exclusion, wait, timeout |
| Fencing token | Block stale holders after lease expiry |
| `SELECT … FOR UPDATE` | Atomic balance invariant in the ledger |
| Idempotency key | Retries must not double-debit |

## Follow-up cheat sheet

| Question | Crisp answer |
|---|---|
| Why not Redis alone? | Lease can expire mid-work; the ledger must enforce balance |
| Why not Postgres alone? | Fine for one DB; Redis helps coordinate multi-instance / multi-row prep |
| Where does Kafka sit? | Async audit only — never inside acquire → commit |
| Same request twice? | Unique `idempotency_keys` row returns the first result |
| Pod killed holding lock? | TTL expires → recovery reads 3PL state → abort or finish → fence protects |
| How do you avoid deadlock? | Lock account ids in sorted order; abort one side if a cycle remains |
