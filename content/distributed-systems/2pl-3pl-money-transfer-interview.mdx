## How to use (5 / 10 min)

Interview problem: **Account A = ₹10,000**. Two requests hit at once — A→B ₹7,000 and A→C ₹6,000. Only one can succeed; balance never goes negative.

## Spoken answer (30 seconds)

```text
I serialize account writes with a Redis exclusive lease (strict 2PL: hold until commit/rollback),
use fencing tokens so a stale holder cannot write after lease expiry,
and make PostgreSQL SELECT … FOR UPDATE the final balance guardian.
Idempotency key stops double debit on retry. Kafka is for lifecycle events only — not on the lock path.
If the app crashes mid-flight, recovery continues or aborts from persisted 3PL state.
```

## Concurrent transfers (the interview scenario)

A=10000. T1 wants 7000, T2 wants 6000. Combined 13000 > 10000.

<Mermaid chart={`sequenceDiagram

  participant P as PostgreSQL

  T2->>R: Lock A wait
  T1->>P: FOR UPDATE + debit 7000

  T1->>R: unlock A

`} />

**Outcome:** one COMPLETED, one FAILED. A is 3000 or 4000 — never negative.

## Deadlock

Lock accounts in **sorted id order** to reduce this. Detector aborts one waiter if a wait-for cycle appears.

<Mermaid chart={`sequenceDiagram
  participant T1 as Tx1
  participant T2 as Tx2
  participant R as Redis

  T1->>R: Lock A
  T2->>R: Lock B
  T1->>R: wait B
  T2->>R: wait A
  R-->>T2: DEADLOCK → abort T2
  T2->>R: release B
  T1->>R: get B → continue
`} />

## Basic implementation (interview-sized)

### 1) Redis exclusive lock + safe unlock

```java
// acquire
Boolean ok = redis.setIfAbsent("lock:" + accountId, token, Duration.ofSeconds(30));

// unlock — only owner may delete (Lua)
String lua = """
  if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
  else return 0 end
  """;
```

### 2) PostgreSQL final guardian

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select a from Account a where a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") String id);

@Transactional
public void apply(String src, String dst, BigDecimal amount) {
  Account a = repo.findByIdForUpdate(min(src, dst)).orElseThrow();
  Account b = repo.findByIdForUpdate(max(src, dst)).orElseThrow();
  // map a/b back to src/dst, then:
  if (source.getBalance().compareTo(amount) < 0) throw new InsufficientFunds();
  source.debit(amount);
  dest.credit(amount);
}
```

### 3) Transfer flow (strict 2PL)

```java
public TransferResult transfer(req) {
  if (idempotency.exists(req.key())) return idempotency.get(req.key());

  String[] keys = sorted(req.from(), req.to()); // deadlock avoidance
  LockToken t1 = locks.acquire(keys[0]);
  LockToken t2 = locks.acquire(keys[1]);
  try {
    accounts.apply(req.from(), req.to(), req.amount()); // FOR UPDATE inside
    idempotency.save(req.key(), COMPLETED);
    return COMPLETED;
  } catch (RuntimeException e) {
    // DB rolled back; still release Redis
    throw e;
  } finally {
    locks.release(t2);
    locks.release(t1);
  }
}
```

### 4) Why both Redis and PG?

| Layer | Job |
|---|---|
| Redis lock | Cross-instance mutual exclusion + wait/timeout |
| Fencing token | Stop stale holder after lease expiry |
| `FOR UPDATE` | Atomic balance invariant in the ledger |
| Idempotency key | Retries do not double-debit |

## Follow-up cheat answers

| Question | Answer |
|---|---|
| Why not Redis alone? | Lease can expire mid-work; ledger must enforce balance |
| Why not PG alone? | Works for one DB; Redis helps coordinate multi-service / multi-row prep |
| Where is Kafka? | Async audit/lifecycle only — never inside acquire→commit |
| Double submit? | Unique `idempotency_keys` row |
| Pod killed holding lock? | TTL expires → recovery reads 3PL state → abort or finish → fence protects |
