## How to use this page

Design a **concurrent money transfer** that never goes negative — not a theory lecture on locking acronyms.

Two requests arrive together:

| Account | Opening balance |
|---|---:|
| **A** | ₹10,000 |
| **B** | ₹5,000 |
| **C** | ₹2,000 |

| Tx | Transfer | Amount |
|---|---|---:|
| **T1** | A → B | ₹7,000 |
| **T2** | A → C | ₹6,000 |

Combined demand is ₹13,000. Only **one** transfer can succeed. Say that outcome before drawing boxes.

## Mental model

```text
Request → idempotency claim → Redis exclusive leases (sorted)
       → PostgreSQL FOR UPDATE → debit/credit → COMMIT
       → safe unlock → COMPLETED
```

| | |
|---|---|
| **WHAT** | Serialize concurrent transfers so the ledger stays correct |
| **HOW** | Strict 2PL on Redis + row locks in Postgres + fencing + idempotency |
| **WHY** | Multiple app instances; retries; lease expiry; crash mid-flight |

### Invariants to defend

| Invariant | Why interviewers care |
|---|---|
| Balance never negative | Core money correctness |
| At-most-once debit per idempotency key | Mobile / gateway retries are normal |
| Locks held until commit or rollback | Strict 2PL — no early release |
| Stale lock holder cannot write | Fencing after lease expiry |
| Kafka off the sync path | Events must not delay locking |

## Spoken answer (30 seconds)

> I serialize account writes with a **Redis exclusive lease** (strict 2PL: hold until commit or rollback), attach a **fencing token** so a stale holder cannot write after lease expiry, and make **PostgreSQL `SELECT … FOR UPDATE`** the final balance guardian. An **idempotency key** stops double debit on retry. **Kafka is lifecycle only** — never inside acquire→commit. If the app crashes mid-flight, recovery continues or aborts from **persisted 3PL state**.

Practice once out loud before the interview.

## 2. Happy path — strict 2PL

Acquire **all** locks → mutate → commit/rollback → **then** release.

<Mermaid chart={`sequenceDiagram
  autonumber
  participant C as Client
  participant T as Transfer
  participant R as Redis
  participant P as PostgreSQL

  C->>T: POST /transfers A→B ₹7000 + Idempotency-Key
  T->>T: Claim unique idempotency key
  T->>R: SET lock:A token NX PX
  R-->>T: OK · fencing = n
  T->>R: SET lock:B token NX PX
  R-->>T: OK · fencing = m
  T->>P: BEGIN
  T->>P: SELECT A,B FOR UPDATE
  T->>P: Debit A / credit B
  T->>P: COMMIT
  T->>R: Lua DEL only if token matches
  T-->>C: status = COMPLETED
`} />

**Say this:** “Locks stay held through the DB transaction. Unlock is compare-and-delete on the token — never a blind `DEL`.”

T1 wants ₹7,000. T2 wants ₹6,000. Combined ₹13,000 > ₹10,000.

  participant P as PostgreSQL

  T1->>R: Lock A acquired
  T2->>R: Lock A — waiting
  T1->>P: FOR UPDATE · debit ₹7000

  R-->>T2: Lock A acquired

  P-->>T2: Insufficient funds
  T2->>T2: ROLLBACK
  T2->>R: Unlock A
`} />

| Result | Detail |
|---|---|
| Winner | One of T1 / T2 → `COMPLETED` |
| Loser | The other → `FAILED` (insufficient funds) |
| Final A | ₹3,000 **or** ₹4,000 — never negative |

## 5. Deadlock

Always lock account ids in **sorted order** to reduce cycles. If a wait-for cycle still appears, abort one waiter.

<Mermaid chart={`sequenceDiagram
  participant T1 as Tx1
  participant T2 as Tx2
  participant R as Redis

  T1->>R: Lock A
  T2->>R: Lock B
  T1->>R: Wait for B
  T2->>R: Wait for A
  R-->>T2: DEADLOCK — abort Tx2
  T2->>R: Release B
  T1->>R: Acquire B · continue
`} />

## Basic implementation (interview-sized)

Four snippets. Enough for the whiteboard — not a multi-module repo dump.

### Redis exclusive lock + safe unlock

```java
// Acquire
Boolean ok = redis.setIfAbsent(
    "lock:" + accountId, token, Duration.ofSeconds(30));

// Unlock — only the owner may delete
String lua = """
  if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
  else
    return 0
  end
  """;
```

### PostgreSQL final guardian

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select a from Account a where a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") String id);

@Transactional
public void apply(String src, String dst, BigDecimal amount) {
  // Lock in sorted id order to reduce deadlocks
  Account first  = repo.findByIdForUpdate(min(src, dst)).orElseThrow();
  Account second = repo.findByIdForUpdate(max(src, dst)).orElseThrow();
  Account source = src.equals(first.getId()) ? first : second;
  Account dest   = source == first ? second : first;

  if (source.getBalance().compareTo(amount) < 0) {
    throw new InsufficientFunds();
  }
  source.debit(amount);
  dest.credit(amount);
}
```

### Transfer flow (strict 2PL)

```java
public TransferResult transfer(TransferRequest req) {
  if (idempotency.exists(req.key())) {
    return idempotency.get(req.key());
  }

  String[] keys = sorted(req.from(), req.to());
  LockToken t1 = locks.acquire(keys[0]);
  LockToken t2 = locks.acquire(keys[1]);
  try {
    accounts.apply(req.from(), req.to(), req.amount());
    idempotency.save(req.key(), COMPLETED);
    return COMPLETED;
  } finally {
    locks.release(t2);
    locks.release(t1);
  }
}
```

### Why both Redis and Postgres?

| Layer | Job in the design |
|---|---|
| Redis exclusive lease | Cross-instance mutual exclusion, wait, timeout |
| Fencing token | Block stale holders after lease expiry |
| `SELECT … FOR UPDATE` | Atomic balance invariant in the ledger |
| Idempotency key | Retries must not double-debit |

## Follow-up cheat sheet

| Question | Crisp answer |
|---|---|
| Why not Redis alone? | Lease can expire mid-work; the ledger must enforce balance |
| Why not Postgres alone? | Fine for one DB; Redis helps coordinate multi-instance / multi-row prep |
| Where does Kafka sit? | Async audit only — never inside acquire → commit |
| Same request twice? | Unique `idempotency_keys` row returns the first result |
| Pod killed holding lock? | TTL expires → recovery reads 3PL state → abort or finish → fence protects |
| How do you avoid deadlock? | Lock account ids in sorted order; abort one side if a cycle remains |
