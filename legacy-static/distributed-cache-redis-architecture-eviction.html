Distributed Cache: Redis Architecture & Eviction

A production-oriented guide to distributed caching with Redis: architecture, cache patterns, TTL, eviction, scaling, consistency and failure handling.

Advanced · SDE II / SDE III / Staff · 10 min read

Core principle: the database remains the source of truth; Redis is an acceleration layer.

1. Why do we need a distributed cache?

Databases provide durable storage, but repeatedly reading the same hot data can increase latency and database load. A distributed cache keeps frequently accessed data closer to the application so reads can be served with lower latency and higher throughput.

Redis is widely used because it is an in-memory data store with rich data structures, expiration, replication and clustering capabilities.

3. Cache-aside pattern

value = redis.get(key)

if value exists:
    return value

value = database.get(id)
redis.set(key, value, TTL)
return value

Cache-aside is popular because the application controls what is cached and when it is populated. The trade-off is that the application must handle misses, invalidation and consistency.

4. Common caching strategies

Cache-aside

Read from cache first. On a miss, read the database and populate the cache.

Write-through

Writes go through the cache and are synchronously propagated to the backing store.

Write-behind

The cache acknowledges writes and persists them asynchronously. This can improve throughput but increases durability complexity.

Read-through

The cache layer loads missing values from the backing store.

5. Redis architecture and scaling

A deployment can be a single instance for simple workloads, replication for higher availability, or Redis Cluster for horizontal scaling. In Redis Cluster, keys are mapped to hash slots distributed across primary nodes. Replicas maintain replicated state and can provide failover capacity.

  • Primary: normally handles writes and serves reads.
  • Replica: maintains replicated state and can take over after primary failure.
  • Cluster: distributes hash slots across multiple primaries.
  • Client: should understand cluster routing or use a cluster-aware library.

6. TTL: time-to-live

TTL limits how long a cached entry remains valid. Choose TTL based on freshness requirements, traffic patterns, database load and the business impact of stale data.

7. Redis eviction

When memory is constrained, Redis can remove keys according to its configured max-memory policy.

LRU — Least Recently Used

Evicts keys that appear less recently accessed. Useful when recency predicts future access.

LFU — Least Frequently Used

Evicts keys with lower access frequency. Useful when a small set of keys remains consistently hot.

TTL-based policies

Some policies restrict eviction candidates to keys with expiration.

No eviction

A no-eviction policy rejects writes when memory is exhausted, so the application must handle write failures.

8. Eviction vs expiration

Expiration happens because a key's TTL reaches zero. Eviction happens because Redis needs to free memory according to its configured policy.

9. Cache stampede

If a popular key expires and many requests miss simultaneously, they can all hit the database. Mitigations include request coalescing, distributed locks, early refresh and randomized TTL jitter.

baseTTL = 300 seconds
jitter  = random(0..60 seconds)
TTL     = baseTTL + jitter

10. Cache penetration and avalanche

Cache penetration

Requests repeatedly ask for data that does not exist. Negative caching, validation and Bloom filters can reduce unnecessary database lookups.

Cache avalanche

Many keys expire around the same time, producing a sudden database load spike. TTL jitter and staggered refresh help spread load.

11. Consistency and invalidation

The hardest cache problem is often invalidation. Decide whether the system requires strong consistency, bounded staleness or eventual consistency. Common approaches are delete-on-write, update-on-write, event-driven invalidation and short TTLs.

12. Production checklist

  • Define cache ownership and invalidation strategy.
  • Choose TTLs based on freshness requirements.
  • Monitor hit ratio, memory, evictions, latency and connections.
  • Protect against stampedes with locking, coalescing or refresh-ahead.
  • Use cluster-aware clients for Redis Cluster.
  • Define behavior when Redis is unavailable.
  • Never assume cached data is permanently available.
  • Protect sensitive data with appropriate isolation and access controls.

14. SDE III / Staff-level discussion

At senior levels, focus on trade-offs: consistency versus latency, memory versus hit ratio, centralized versus local caching, failure isolation, hot-key mitigation, operational cost and system behavior when the cache is unavailable.

Key takeaway

A distributed cache should not be added simply because it is fast. Design it around access patterns, freshness requirements, failure modes, memory limits and the source of truth. Redis provides the primitives; architecture determines whether the system is resilient.
